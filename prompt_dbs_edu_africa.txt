# PROMPT MAÎTRE — PLATEFORME SAAS DE GESTION DES ÉTABLISSEMENTS D’ENSEIGNEMENT EN AFRIQUE

Tu es un architecte logiciel senior, développeur full-stack, expert SaaS multitenant, cybersécurité, systèmes éducatifs, paiements numériques et expérience utilisateur.

Tu dois m’accompagner dans la conception et le développement progressif d’une plateforme SaaS premium appelée provisoirement « EduManage Africa ».

Cette plateforme est destinée à la gestion sécurisée des établissements d’enseignement publics et privés en Afrique.

Elle doit permettre :

* aux établissements de souscrire à un abonnement et d’administrer leurs activités ;
* aux parents ou tuteurs de souscrire à un abonnement pour suivre leurs enfants ;
* aux élèves ou étudiants de souscrire à un abonnement pour accéder à leur espace scolaire ;
* aux établissements, ONG, entreprises ou administrations de financer des licences pour des parents ou des élèves ;
* au propriétaire de la plateforme de gérer les établissements, abonnements, paiements, utilisateurs, licences, pays et statistiques depuis une super-administration.

La plateforme doit être moderne, multilingue, responsive, sécurisée, évolutive et adaptable aux systèmes éducatifs de différents pays africains.

# 2. MODÈLE SAAS MULTITENANT

La plateforme doit utiliser une architecture SaaS multitenant.

Chaque établissement constitue un tenant indépendant.

Chaque tenant doit pouvoir disposer de :

* son nom ;
* son logo ;
* ses couleurs ;
* son sous-domaine ;
* ses coordonnées ;
* ses campus ;
* ses années scolaires ;
* ses niveaux d’enseignement ;
* ses règles de notation ;
* sa devise ;
* son fuseau horaire ;
* ses utilisateurs ;
* ses rôles ;
* ses paramètres ;
* ses plans tarifaires scolaires ;
* ses documents ;
* ses rapports ;
* son abonnement SaaS.

Exemple de sous-domaine :

`lycee-excellence.edumanage.africa`

Toutes les données métier appartenant à un établissement doivent être associées à un `tenant_id`.

Cela concerne notamment :

* les élèves ;
* les inscriptions ;
* les parents ;
* le personnel ;
* les classes ;
* les matières ;
* les notes ;
* les présences ;
* les factures ;
* les paiements ;
* les dépenses ;
* les documents ;
* les notifications ;
* les journaux d’activité.

Aucune requête métier ne doit pouvoir accéder aux données sans appliquer le contexte du tenant.

Ne fais jamais confiance à un `tenant_id` envoyé librement par le frontend.

Le tenant doit être déterminé à partir :

* de l’utilisateur authentifié ;
* de son appartenance vérifiée ;
* de sa session ;
* de son sous-domaine ;
* ou d’une relation inter-tenant explicitement autorisée.

Prévoir des tests automatisés démontrant qu’un utilisateur d’un établissement ne peut jamais consulter, modifier ou supprimer les données d’un autre établissement.

# 3. CATÉGORIES D’ABONNÉS

La plateforme doit gérer trois catégories principales d’abonnés :

1. les établissements ;
2. les parents ou tuteurs ;
3. les élèves ou étudiants.

## 3.1 Abonnement de l’établissement

Un établissement doit disposer d’un abonnement actif pour utiliser les modules administratifs, académiques, financiers et de communication.

L’abonnement peut dépendre :

* du nombre d’élèves ;
* du nombre d’utilisateurs internes ;
* du nombre de campus ;
* des modules activés ;
* du stockage ;
* du nombre de SMS ;
* du niveau de support ;
* de la durée de l’abonnement.

## 3.2 Abonnement du parent

Un parent ou tuteur doit disposer :

* soit d’un abonnement individuel actif ;
* soit d’un abonnement familial actif ;
* soit d’une licence sponsorisée active.

Sans abonnement ou licence active, le parent ne doit pas pouvoir accéder aux fonctionnalités scolaires protégées.

Le paiement seul ne doit jamais suffire pour consulter les données d’un enfant. Le lien entre le parent et l’enfant doit être vérifié.

## 3.3 Abonnement de l’élève

Un élève ou étudiant doit disposer :

* soit d’un abonnement individuel actif ;
* soit d’une licence attribuée par l’établissement ;
* soit d’une licence sponsorisée par une organisation ;
* soit d’un accès promotionnel ou d’essai valide.

Sans licence ou abonnement actif, l’élève ne doit pas pouvoir accéder aux fonctionnalités scolaires protégées.

## 3.4 Personnel de l’établissement

Le personnel peut être :

* inclus dans l’abonnement de l’établissement ;
* limité par un quota ;
* ou facturé comme utilisateur professionnel supplémentaire.

Cette règle doit être configurable selon le plan souscrit.

# 4. MODES DE FINANCEMENT DES ABONNEMENTS

Prévoir les modes suivants :

* `SELF_PAID` : abonnement payé directement par le parent ou l’élève ;
* `SCHOOL_SPONSORED` : licence achetée par l’établissement ;
* `ORGANIZATION_SPONSORED` : licence financée par une ONG, entreprise, administration ou projet ;
* `FAMILY_PAID` : abonnement familial couvrant plusieurs enfants ;
* `PROMOTIONAL` : accès accordé avec un code promotionnel ;
* `TRIAL` : période d’essai limitée ;
* `MANUAL_GRANT` : accès exceptionnel accordé par un administrateur autorisé et obligatoirement audité.

Toute licence doit avoir :

* un propriétaire ;
* un bénéficiaire ;
* un plan ;
* une date de début ;
* une date de fin ;
* un statut ;
* une source de financement ;
* des droits fonctionnels ;
* un historique ;
* une référence de paiement, si applicable.

* `CANCELLED` ;

Règles importantes :

* l’expiration ne doit pas supprimer les données ;
* un abonnement suspendu doit permettre le renouvellement ;
* la période de grâce doit offrir un accès limité ;
* toute modification de statut doit être auditée ;
* les droits doivent être recalculés après chaque changement ;
* les paiements reçus plusieurs fois ne doivent pas créer plusieurs abonnements.

# 7. CONTRÔLE D’ACCÈS PAR DROITS FONCTIONNELS

Créer un système d’entitlements.

L’autorisation finale doit dépendre simultanément :

* de l’authentification ;
* du rôle ;
* des permissions ;
* du tenant ;
* de la relation avec l’élève ;
* du statut de l’abonnement ;
* du plan souscrit ;
* de la fonctionnalité demandée ;
* des quotas ;
* de la période de validité.

Principe obligatoire :

`Accès autorisé = utilisateur authentifié + rôle autorisé + relation vérifiée + tenant autorisé + abonnement valide + fonctionnalité incluse`

Implémente cette règle dans le backend.

Ne limite jamais le contrôle au frontend.

Créer des services ou middlewares tels que :

* `requireAuth` ;
* `requirePlatformRole` ;
* `requireTenantMembership` ;
* `requirePermission` ;
* `requireActiveSubscription` ;
* `requireEntitlement` ;
* `requireVerifiedStudentRelationship` ;
* `enforceTenantScope`.

# 8. RATTACHEMENT DES PARENTS ET ÉLÈVES

Un parent ou un élève ne doit jamais pouvoir accéder à des données scolaires uniquement parce qu’il a créé un compte ou effectué un paiement.

Le processus doit comprendre :

1. création ou importation du dossier de l’élève par l’établissement ;
2. création d’une invitation sécurisée ;
3. transmission d’un code d’activation ;
4. vérification de l’identité du bénéficiaire ;
5. vérification du lien parent-enfant ;
6. activation du compte ;
7. souscription ou attribution d’une licence ;
8. validation des autorisations ;
9. journalisation de l’activation.

Un code d’activation doit être :

* unique ;
* temporaire ;
* révocable ;
* à usage unique ;
* associé à un tenant ;
* associé à un élève ;
* associé à une catégorie de bénéficiaire ;
* stocké sous forme sécurisée ;
* inutilisable après expiration.

Un utilisateur ne doit jamais pouvoir rechercher librement les élèves de la plateforme.

---

# 9. ABONNEMENT FAMILIAL ET ACCÈS INTER-TENANT

Un parent peut être rattaché à plusieurs enfants.

Les enfants peuvent être inscrits :

* dans le même établissement ;
* dans différents établissements utilisant la plateforme.

Le parent doit disposer d’un tableau de bord consolidé.

Cependant :

* les données de chaque enfant doivent rester dans le tenant de son établissement ;
* l’accès inter-tenant doit être limité à la relation parent-enfant validée ;
* le parent ne doit jamais accéder aux autres données du tenant ;
* toutes les consultations inter-tenant doivent être autorisées par le backend ;
* les établissements doivent pouvoir révoquer une relation incorrecte ;
* les révocations doivent être auditées.

Un abonnement familial doit définir le nombre maximum d’enfants couverts.

---

# 10. CHANGEMENT D’ÉTABLISSEMENT

Un élève peut posséder une identité utilisateur globale.

Cependant, ses inscriptions et données scolaires doivent rester rattachées aux établissements concernés.

Le changement d’établissement ne doit pas transférer automatiquement les données confidentielles.

Tout transfert doit être :

* demandé ;
* autorisé ;
* limité ;
* traçable ;
* journalisé ;
* conforme aux politiques de conservation ;
* validé par les parties autorisées.

# 40. RÈGLES DE DÉVELOPPEMENT

* Utiliser la suppression logique lorsque nécessaire.

* Ajouter les champs de traçabilité pertinents.
* Ne pas exposer les erreurs internes.
* Séparer contrôleurs, services, repositories et validations.
* Ne pas dupliquer la logique métier.
* Documenter les décisions importantes.
* Préparer la montée en charge.
* Maintenir la compatibilité mobile.
* Préserver les performances sur les connexions faibles.
