## Stratégie multitenant (implémentée, Phase 2)

Deux couches de défense indépendantes, aucune ne suffisant seule :

1. **Extension Prisma** ([apps/api/src/lib/prisma.ts](../apps/api/src/lib/prisma.ts)) : intercepte chaque opération sur les modèles listés dans `TENANT_SCOPED_MODELS` ([tenant-scoped-models.ts](../apps/api/src/lib/tenant-scoped-models.ts), 64 modèles) et fusionne/valide `tenantId` contre le contexte `AsyncLocalStorage` posé par `enforceTenantScope`. Une requête sans contexte tenant lève une erreur plutôt que de s'exécuter sans filtre.
2. **Row-Level Security PostgreSQL** (migrations `enable_row_level_security` + corrections listées ci-dessous) : chaque opération scopée passe par une micro-transaction qui exécute `SELECT set_config('app.tenant_id', <tenantId>, true)` avant la requête réelle — le même mécanisme protège même un accès qui contournerait l'extension applicative.

**Le rôle applicatif ne doit jamais être le superuser Postgres** : RLS est totalement ignorée pour un superuser ou un rôle `BYPASSRLS`, quel que soit `FORCE ROW LEVEL SECURITY`. L'app tourne sous un rôle dédié `edumanage_app` (créé manuellement, hors migration versionnée — voir `docs/architecture.md#notes-denvironnement-de-développement`), avec uniquement les privilèges DML nécessaires.

**Exceptions RLS documentées** — quatre tables n'ont jamais ou plus RLS active, chacune via une migration dédiée expliquant pourquoi :

- `TenantDomain` : résoudre un sous-domaine vers un tenant est par nature une lecture _avant_ qu'aucun contexte tenant n'existe (c'est justement ce que cette requête établit). RLS rendrait ce bootstrap impossible.
- `ParentStudentRelationship` : même catégorie de problème — retrouver le tenant d'un enfant à partir de `(parentUserId, studentId)` doit fonctionner avant que le tenant ne soit connu (§9, portail parent multi-établissement). Le lookup reste sûr car c'est toujours une clé composite exacte, jamais un scan, et le statut `VERIFIED` + l'absence de révocation restent vérifiés par le middleware.
- `ActivationInvitation` : `redeemActivation` (§8) résout le tenant DEPUIS le code d'activation, avant tout contexte tenant établi — même bootstrap, lookup ponctuel par clé sur un identifiant que l'appelant possède déjà (`20260812090000_activation_invitation_no_rls`).
- `StudentUserLink` : `requireLinkedStudent` (§26) a le même besoin côté élève que `requireVerifiedStudentRelationship` côté parent — jamais activée dès sa création avec `tenantId` (`20260813090037_student_user_link_tenant_id`), plutôt que désactivée après coup.

Toute future table jouant ce rôle de « point d'entrée de résolution de tenant » doit suivre le même traitement, avec la même justification enregistrée dans sa migration.

**Correctif (audit de couverture complet §1-§41)** : `StudentInvoiceItem`, `ReportCardItem` et `GradeChangeLog` (lignes filles sans `tenantId` propre, protégées jusque-là uniquement par leur relation à un parent tenant-scopé) et `StudentTransfer` (le seul modèle réellement inter-tenant, `fromTenantId`/`toTenantId`, jusque-là ni gardé ni RLS) n'avaient aucune protection base de données — un accès direct via `rawPrisma` sans passer par le service applicatif contournait entièrement l'isolation. Fermé par la migration `rls_child_tables_and_transfers` :

- `StudentInvoiceItem`/`ReportCardItem`/`GradeChangeLog` : politique RLS par sous-requête vers le `tenantId` du parent (`StudentInvoice`/`ReportCard`/`Grade`). Sûr sans changement de code pour `StudentInvoiceItem` (jamais interrogé hors écriture imbriquée/`include` sous son parent déjà gardé) ; `report-card.service.ts` et `grade.service.ts` enveloppent désormais leurs quelques appels directs restants dans `withTenantSession` pour garantir que `app.tenant_id` est positionné au moment où Postgres évalue la politique.
- `StudentTransfer` : politique `fromTenantId = current_setting(...) OR toTenantId = current_setting(...)` — visible pour l'un ou l'autre établissement partie au transfert, jamais un tiers. `transfer.service.ts` enveloppe désormais chaque requête dans `withTenantSession(tenantId, ...)` plutôt que d'appeler `rawPrisma.studentTransfer` nu. Prouvé au niveau base par un test qui parle directement à Postgres sous le rôle `edumanage_app` (même style que le test RLS de `tenant-isolation.test.ts`).

**Restent délibérément sans RLS, pour les mêmes raisons déjà documentées ci-dessus (lookup légitimement cross-tenant ou multi-tenant par nature) :**

- `ActivationCode` : la rédemption résout par `codeHash`, avant qu'aucun contexte tenant n'existe — même bootstrap qu'`ActivationInvitation`.
- `SupportTicketMessage` : lu/écrit par la super-administration à travers tous les tenants (`support-ticket-admin.service.ts`) — imposer RLS casserait cet usage légitime.
- `FamilyAccount`/`Guardian`/`FamilyMember` : pas des tables tenant-scopées au sens propre — une famille couvre par construction plusieurs établissements (§9).
- `Notification`/`MessageTemplate`/`SupportTicket`/`Document`/`UserRole`/`AuditLog`/`SubscriptionOwner` : `tenantId` nullable par conception (globaux OU tenant-spécifiques, voir `tenant-scoped-models.ts`) — leur donner une RLS correcte demande d'étendre le garde applicatif pour distinguer les deux cas plutôt qu'un correctif ponctuel ; identifié comme chantier séparé, pas traité ici pour éviter de casser silencieusement les usages plateforme-large existants (une politique naïve rendrait `app.tenant_id` obligatoire pour des lectures qui ne le positionnent jamais aujourd'hui).

**Limite connue** : le garde applicatif enveloppe chaque appel Prisma dans sa propre micro-transaction. Un service qui a besoin de plusieurs écritures scopées atomiques ensemble (ex. opération financière débitant une ligne et créditant une autre, §23/§40) ne doit pas compter sur ce comportement seul. Note Phase 3 : pour les modèles NON tenant-scopés (Subscription, Invoice, PaymentTransaction, ...), ce n'est pas un problème — `payment.service.ts` compose `prisma.$transaction(tx => ...)` avec `applySubscriptionTransition(tx, ...)` directement, une seule transaction couvrant paiement + facture + abonnement + reçu (voir `handleSuccessfulTransaction`). Résolu en Phase 4 pour les écritures **tenant-scopées** atomiques ensemble : `withTenantSession(tenantId, fn)` ([apps/api/src/lib/prisma.ts](../apps/api/src/lib/prisma.ts)) ouvre une seule `rawPrisma.$transaction`, positionne `app.tenant_id` une fois, puis expose le client transactionnel brut — première utilisation réelle dans `tenant.service.ts` (création de la `TenantMembership` + du `UserRole` SCHOOL_OWNER en une seule transaction).

Tests d'isolation (Phase 2, [apps/api/src/test/integration/](../apps/api/src/test/integration/)) : 23 tests couvrant l'extension Prisma + RLS directement, la chaîne RBAC complète, `requireActiveSubscription`/`requireEntitlement` (y compris quotas et non-suppression des données à l'expiration), et `requireVerifiedStudentRelationship` (enfants vérifiés, multi-tenant, révocation immédiate, paiement seul insuffisant).

## Journalisation d'audit des actions tenant-internes sensibles — finalisation Phase 2

`recordAuditLog` ([lib/audit-log.ts](../apps/api/src/lib/audit-log.ts)) n'était exercé que côté super-admin (§31) depuis sa création — aucune action tenant-interne ordinaire n'écrivait d'`AuditLog`, seul point resté explicitement hors périmètre Phase 2. Fermé pour les actions tenant-internes **sensibles au sens RBAC/sécurité** (attribution de privilège, révocation d'accès, mouvement d'argent) plutôt que pour toute mutation de ce code — auditer un devoir déposé ou une présence prise n'apporte rien à la piste de sécurité que cette phase visait, et transformerait chaque service métier en écrivain d'audit sans bénéfice proportionné.

- **[lib/tenant-actor.ts](../apps/api/src/lib/tenant-actor.ts)** : `resolveTenantActor(req)`, même forme que `PlatformActor` (§31, [platform-actor.ts](../apps/api/src/modules/platform-admin/platform-actor.ts)) mais sans `justification` obligatoire — résout `req.user.id` + un rôle tenant actif (`getTenantRoleCodes`, nouvel export de [lib/authorization.ts](../apps/api/src/lib/authorization.ts), même `activeRoleCodes` interne que `getPlatformRoleCodes`) pour `actorRoleCode`.
- **Six actions désormais auditées**, chacune avec `tenantId`/`actorUserId`/`actorRoleCode` et un `beforeData`/`afterData` minimal :
  - `tenant_user.role_grant` / `tenant_user.role_revoke` / `tenant_user.membership_status_update` ([tenant-user.service.ts](../apps/api/src/modules/tenant-users/tenant-user.service.ts), §17) — qui peut agir en tant que qui dans un tenant.
  - `activation_invitation.revoke` ([activation-invitation.service.ts](../apps/api/src/modules/family/activation-invitation.service.ts), §8) et `parent_student_relationship.revoke` ([parent-student-relationship.service.ts](../apps/api/src/modules/family/parent-student-relationship.service.ts), §9) — coupent l'accès d'un bénéficiaire, `revokedReason`/`reason` (déjà obligatoire au schéma pour la seconde) alimente aussi `justification` sur l'entrée d'audit plutôt que de dupliquer un motif.
  - `student_invoice.cancel` ([student-invoice.service.ts](../apps/api/src/modules/finance/student-invoice.service.ts)) et `student_payment.refund` ([student-payment.service.ts](../apps/api/src/modules/finance/student-payment.service.ts), §23) — mouvements financiers.
- **Consultation** : même route super-admin que §31 (`GET /platform/audit-logs?tenantId=&entityType=`), `AuditLog` n'étant pas un modèle tenant-scoped (pas de nouvelle route tenant-facing pour ce périmètre) — testé dans [phase2-tenant-audit-log.test.ts](../apps/api/src/test/integration/phase2-tenant-audit-log.test.ts).

**Restent hors périmètre, par choix (pas des trous de sécurité)** : mutations pédagogiques/administratives ordinaires (notes, devoirs, présences, documents...) — aucune n'ajuste un privilège ou ne déplace de l'argent ; `AuditLog` lui-même n'a pas de politique de rétention/export dédiée (hors sujet de cette finalisation).

## Modèle d'abonnement (implémenté, Phase 2)

- `Subscription` rattaché à un `SubscriptionOwner` polymorphe (`Tenant`, `FamilyAccount`, `Student` ou `Organization`) via des FK nullables + discriminant `ownerType` (Prisma ne supporte pas les FK polymorphes natives) — table séparée plutôt que des champs directs sur `Subscription`, pour que `BillingAccount` et `LicenseAssignment` référencent le même point d'ancrage sans dupliquer la logique polymorphe.
- Statuts (`DRAFT`…`REFUNDED`) et transitions tracées via `SubscriptionEvent` (immuable). Machine à états implémentée en Phase 3 (voir ci-dessous).
- Le lien parent-enfant (`ParentStudentRelationship`) est indépendant du paiement : il naît uniquement du parcours d'activation sécurisé (invitation → code d'activation à usage unique, haché, jamais stocké en clair → vérification → activation), jamais d'une simple déclaration ou d'un paiement — testé explicitement.
- Le tableau de bord parent consolidé interroge chaque tenant séparément avec le contexte de l'enfant concerné (voir `requireVerifiedStudentRelationship`) — jamais de jointure cross-tenant en base.

Schéma complet : `prisma/schema/*.prisma` (14 fichiers par domaine, 113 modèles).

## Abonnements et paiements (implémenté, Phase 3)

**Machine à états** ([subscription.service.ts](../apps/api/src/modules/subscriptions/subscription.service.ts) + [subscription-transitions.ts](../apps/api/src/modules/subscriptions/subscription-transitions.ts)) : table `ALLOWED_SUBSCRIPTION_TRANSITIONS` explicite (§6) — `CANCELLED`/`REFUNDED` terminaux, pas de saut direct `DRAFT` → `ACTIVE`. Chaque transition, dans une seule transaction : valide le changement, marque `startsAt`/`endsAt`/`cancelledAt` selon le cas, écrit un `SubscriptionEvent` immuable, recalcule les `Entitlement` depuis `PlanFeature` (activés seulement si le nouveau statut est `ACTIVE`/`TRIAL`/`GRACE_PERIOD` — jamais supprimés, juste désactivés, données préservées).

**Architecture adaptateur paiement** ([payment-providers/](../apps/api/src/modules/payments/payment-providers/)) : interface `PaymentProviderAdapter` (vérification de signature + parsing normalisé). Un seul flux est réellement opérationnel pour l'instant :

- **Espèces (`CASH_AGENT`)** : synchrone, pas de webhook — un agent autorisé enregistre le paiement, qui déclenche immédiatement facture payée + abonnement actif + reçu.
- **Mobile Money (Orange Money, MTN MoMo, M-Pesa, Airtel Money)** : **non branché** — aucun contrat opérateur ni identifiants sandbox à ce jour. `HmacSignedProviderAdapter` est un adaptateur de référence (HMAC-SHA256 sur le corps brut, schéma courant chez plusieurs opérateurs) servant de modèle et de banc de test — à dupliquer et ajuster contre la documentation réelle de chaque opérateur avant mise en production. `registry.ts` n'a donc aucun adaptateur réel enregistré par défaut : enregistrer un adaptateur y suffit pour activer un opérateur, sans toucher au reste du pipeline (§24).

**Webhook générique** (`POST /api/v1/payments/webhooks/:providerCode`) : monté avec un parseur de corps brut (`express.raw`) **avant** le `express.json()` global — la vérification de signature a besoin des octets exacts. Idempotence à deux niveaux : `PaymentWebhookEvent` unique par `(providerId, externalEventId)`, et `PaymentTransaction` unique par `(providerId, externalReference)` — une livraison dupliquée déclenche une contrainte unique, interceptée et traitée comme un no-op plutôt qu'une erreur.

**Chaîne facture → paiement** : `Invoice` (priorité tarifaire via `PlanPrice`, avec repli pays-spécifique → générique) → `PaymentIntent` (idempotent par `idempotencyKey`, fournie par le client ou générée) → `PaymentTransaction` → `handleSuccessfulTransaction` (marque la facture payée, active l'abonnement si transition valide, émet un reçu — le tout dans une seule transaction, idempotent si rejoué). Chaque étape appelée depuis les routes `/api/v1/subscriptions/school/*` revérifie que la ressource appartient bien au tenant de l'appelant (`assertInvoiceBelongsToSubscription`, `assertPaymentIntentBelongsToSubscription`) — jamais de confiance dans un id fourni par le client.

Tests (Phase 3, [apps/api/src/test/integration/](../apps/api/src/test/integration/) + tests unitaires co-localisés) : transitions valides/invalides, recalcul des entitlements (activation et expiration), flux espèces de bout en bout avec double appel idempotent, garde-fou cross-tenant sur le paiement, webhook signature valide/invalide/dupliquée.

**Correctif partiel (audit de couverture complet §1-§41) — cycle de vie du statut d'abonnement, §6 :** deux constats distincts sous ce même point, l'un fermé, l'autre non.

- **Fermé.** `GRACE_PERIOD` se comportait exactement comme `ACTIVE` — même `isActiveLike`, aucune dégradation malgré §6 (« la période de grâce doit offrir un accès limité »). `recalculateEntitlements` gèle désormais à `0` le `quotaLimit` de toute fonctionnalité déjà plafonnée pendant la grâce (plus aucune nouvelle consommation), sans jamais retirer la fonctionnalité du plan (`isEnabled` reste `true`) ni toucher aux fonctionnalités illimitées — celles-ci ne sont pas la ressource que la grâce cherche à protéger. Testé dans [subscription-lifecycle.test.ts](../apps/api/src/test/integration/subscription-lifecycle.test.ts) : `report_card.download` (quota réel sur `STUDENT_BASIC`, contrairement aux plans `SCHOOL_*` qui l'ont illimité) tombe à quota `0` en `GRACE_PERIOD`, remonte à sa valeur normale en revenant `ACTIVE`.
- **Fermé (chantier séparé, complété).** Rien ne faisait jamais avancer un abonnement dans le temps : aucun scheduler, job ou cron n'existe nulle part dans le dépôt (`apps/worker` n'a aucun consommateur), donc `PAST_DUE → GRACE_PERIOD → EXPIRED` ne se produisait jamais automatiquement. Fermé par vérification paresseuse plutôt que par un job planifié (`apps/worker` n'a toujours aucun consommateur) : `Subscription.currentPeriodEndsAt` (nouveau champ) est calculé par `computePeriodEnd` ([subscription-transitions.ts](../apps/api/src/modules/subscriptions/subscription-transitions.ts)) à chaque entrée en `ACTIVE`, à partir de `billingPeriod` — `null` pour `CUSTOM`, dont la durée réelle n'est trackée nulle part, et approximé à 12 mois calendaires pour `SCHOOL_YEAR` plutôt qu'aligné sur `AcademicYear.endDate` (un abonnement n'est pas toujours porté par un tenant). `advanceSubscriptionIfDue` ([subscription.service.ts](../apps/api/src/modules/subscriptions/subscription.service.ts)) consulte cette date (et `graceEndsAt`/`trialEndsAt`) et fait avancer le statut d'un cran si elle est dépassée — `ACTIVE` va directement en `GRACE_PERIOD` si le plan en accorde une, sinon droit en `EXPIRED` (nouvelle transition directe `ACTIVE → GRACE_PERIOD`, §6). Deux points d'appel : paresseux, dans `findActiveSubscription` ([lib/subscription-access.ts](../apps/api/src/lib/subscription-access.ts)) — point d'entrée unique de toute vérification d'abonnement, donc rattrape tout abonnement réellement consulté avant de statuer sur l'accès ; et `POST /api/v1/platform/subscriptions/sweep-expired` (super-admin) pour les abonnements que personne ne consulte plus activement. Testé dans [subscription-lifecycle.test.ts](../apps/api/src/test/integration/subscription-lifecycle.test.ts) (les quatre transitions temporelles), [subscription-access.test.ts](../apps/api/src/test/integration/subscription-access.test.ts) (rattrapage paresseux, accès toujours accordé/refusé selon le statut avancé) et [platform-admin-subscriptions.test.ts](../apps/api/src/test/integration/platform-admin-subscriptions.test.ts) (balayage plateforme).

**Hors périmètre Phase 3** : licences sponsorisées de bout en bout (`SponsoredLicense`/`LicenseBatch`/`LicenseAssignment` existent dans le schéma mais aucun service ne les pilote encore), codes promotionnels, abonnements parent/élève en libre-service (bloqués par l'absence d'authentification élève-via-`StudentUserLink`, voir Phase 5+), tarification par pays réelle (le seed n'a que des prix génériques XAF).

## Site public et inscription établissement (implémenté, Phase 4)

**Inscription établissement** ([tenant.service.ts](../apps/api/src/modules/tenants/tenant.service.ts), `POST /api/v1/tenants/onboarding`, authentifié mais sans tenant résolu — délibérément pas de `enforceTenantScope`, puisqu'aucun tenant n'existe encore) :

1. Valide pays/devise (référentiels seedés) et unicité du sous-domaine.
2. Crée `Tenant` + `TenantDomain` (statut `PENDING_VERIFICATION`, `verifiedAt` posé immédiatement — le parcours d'inscription lui-même constitue la vérification) dans une seule `rawPrisma.$transaction`.
3. Crée `TenantMembership` + `UserRole` (`SCHOOL_OWNER`) via `withTenantSession` (voir ci-dessus).
4. Crée optionnellement un abonnement `DRAFT` si un `planCode` est fourni.

Pas d'atomicité unique couvrant les étapes 2 et 3 (générer les ids à l'avance a été envisagé et écarté comme fragile) : en cas d'échec de l'étape 3, nettoyage compensatoire explicite (suppression du domaine puis du tenant) dans un `catch`.

**Site public** ([apps/web/src/pages/marketing/](../apps/web/src/pages/marketing/)) : accueil, tarifs (grille par catégorie — établissement/parent/élève, alimentée par les codes de plan seedés), contact (formulaire client uniquement, pas d'endpoint backend — voir Phase 10), pages légales (CGU/confidentialité/remboursement, bandeau « brouillon »), et l'assistant d'inscription multi-étapes (`SignupPage.tsx` : compte → établissement → formule → vérification → soumission `registerAccount` → `login` → `onboardTenant`). Bilingue via le namespace i18next `marketing` (fr par défaut, en secondaire — voir [packages/i18n/](../packages/i18n/)).

## Gestion de l'établissement (implémentée, Phase 5)

Modules REST sous `enforceTenantScope + requireTenantMembership + requirePermission`, un router par domaine, montés dans [app.ts](../apps/api/src/app.ts) :

- **Configuration** ([school-config](../apps/api/src/modules/school-config/)) : campus, années/périodes académiques, cycles/niveaux, classes, départements/matières, programmes, coefficients par matière/niveau. Lecture ouverte à tout membre du tenant, écriture derrière `tenant.settings.manage`.
- **Utilisateurs** ([tenant-users](../apps/api/src/modules/tenant-users/)) : invitation (crée le `User` s'il n'existe pas encore, mot de passe aléatoire jamais communiqué — passe obligatoirement par reset, qui n'existe pas encore comme flux — même absence de fournisseur email réel que la vérification d'inscription, §34), attribution/révocation de rôle, changement de statut de membership. Derrière `tenant.settings.manage`.
- **Personnel** ([employees](../apps/api/src/modules/employees/)) : fiche, statut, archivage (soft delete). Derrière `hr.manage`. §27 complet (contrats, présences, congés, évaluations, documents, export de paie, charges horaires) — voir section dédiée plus bas.
- **Élèves et inscriptions** ([students](../apps/api/src/modules/students/)) : fiche élève (matricule unique par tenant), statut, archivage ; inscription/réinscription (`Enrollment`, une ligne par élève et par année scolaire, `withTenantSession` pour l'écriture combinée inscription + passage `PROSPECTIVE → ACTIVE`). `medicalNotes` accepté en écriture mais jamais renvoyé par l'API générale (`omit` Prisma) — pas encore d'endpoint dédié infirmerie/direction pour le relire (§19). Lecture derrière `students.read` (dont `TEACHER`), écriture derrière `students.write` (`SCHOOL_OWNER`/`SCHOOL_ADMIN`).
- **Documents justificatifs** (`StudentDocument`, dans le même module `students`) : métadonnées uniquement (catégorie + URL fournie par le client, déjà uploadée ailleurs — l'API ne gère aucun octet de fichier), `uploadedByUserId` résolu depuis le token d'auth (jamais depuis le corps de la requête), suppression douce. Mêmes permissions que le reste du module.
- **Détection de doublons** (toujours dans `students`) : heuristique non bloquante — même nom de famille et (prénom identique OU date de naissance identique), insensible à la casse, au sein du même tenant. Renvoyée automatiquement dans `possibleDuplicates` à la création d'un élève, et interrogeable à l'avance via `GET /students/check-duplicates?firstName=&lastName=&dateOfBirth=`. Le volet « configurable » du §19 (activer/désactiver par tenant, ajuster les critères) est différé : il suppose une brique de paramètres tenant (`TenantSetting`) qui n'a pas encore de service ni d'API pour la piloter.
- **Transferts inter-établissements** ([transfer.routes.ts](../apps/api/src/modules/students/transfer.routes.ts), routeur de premier niveau `/api/v1/student-transfers` — pas nested sous `/students`, car le tenant destinataire n'a par définition pas accès au `Student` du tenant source) : workflow en 4 actions sur les 4 statuts de `StudentTransfer` (`REQUESTED → APPROVED/REJECTED → COMPLETED`) — la source demande (destinataire résolu par sous-domaine, jamais par id brut, §8) avec un `dataScope` explicite des champs sensibles autorisés à transiter (jamais un défaut « tout copier », §10) ; le destinataire approuve ou rejette ; la source, une fois approuvé, exécute (`complete`) : crée la fiche chez le destinataire avec un matricule neuf obligatoire et uniquement les champs du `dataScope`, marque l'élève source `TRANSFERRED`. `StudentTransfer` a `fromTenantId`/`toTenantId` plutôt qu'un `tenantId` unique, donc **hors** de la liste auto-scopée par l'extension Prisma (`tenant-scoped-models.ts`) — le service filtre chaque requête explicitement via `rawPrisma`, et toute discordance de partie répond `404` (jamais `403`, même convention que le garde-fou d'extension pour ne jamais confirmer l'existence d'une ressource à qui n'y a pas droit). Les deux écritures de `complete` (création chez le destinataire, mise à jour chez la source) tournent dans deux `withTenantSession` séparés — non atomique à travers la frontière tenant, un choix assumé (voir commentaire dans `transfer.service.ts`).
- **Import/export CSV** (toujours dans `students`) : `POST /students/import` accepte le CSV comme chaîne dans un corps JSON (`{ csv }`), pas d'upload multipart — évite d'ajouter une dépendance de gestion de fichiers pour cette tranche. Parsing via `csv-parse` (jamais un parseur maison — les champs cités contenant des virgules/guillemets sont trop faciles à mal gérer). Chaque ligne est traitée indépendamment via le même `createStudentSchema`/`createStudent` que l'API normale (import partiellement réussi : `{ created, errors }` avec le numéro de ligne d'origine, pas de tout-ou-rien) ; les doublons de matricule au sein du fichier sont détectés avant d'atteindre la base. `GET /students/export` renvoie un CSV en flux, colonnes volontairement limitées (matricule/nom/prénom/naissance/genre/statut — jamais contacts d'urgence, photo ou `medicalNotes`, quel que soit l'appelant) et échappe les valeurs commençant par `=`, `+`, `-`, `@` pour neutraliser l'injection de formule si le fichier est ouvert dans un tableur. Le format Excel (`.xlsx`) natif est différé — un CSV s'ouvre nativement dans Excel, et éviter une dépendance de génération `.xlsx` pour cette tranche est un choix assumé.
- **Cartes scolaires** (`GET /students/:id/id-card`, toujours dans `students`) : PDF généré à la volée avec `pdfkit` (format CR80, aucune dépendance native), contenu texte uniquement — établissement, nom, matricule, date de naissance, classe et année scolaire tirées de l'inscription active la plus récente. Bloqué (`STUDENT_NOT_ENROLLED`, 400) si l'élève n'a aucune inscription `ENROLLED`/`RE_ENROLLED`. La photo n'est délibérément **pas** intégrée : `photoUrl` est une URL externe fournie par le client, et la récupérer côté serveur pour l'incorporer au PDF serait un vecteur SSRF direct sans allowlist/timeout/limite de taille — différé, pas un oubli.

Restent hors périmètre de cette Phase : export/import au format Excel natif, intégration de la photo sur la carte scolaire. Le rattachement parent/élève par invitation + code d'activation (§8) était listé ici comme reporté à la Phase 8 — voir la section dédiée plus bas, désormais fait.

## Ressources humaines — §27 clôturé (Phase 10 démarrée)

Phase 5 n'avait construit que la fiche personnel (`Employee` : identité, statut, archivage). Le schéma (`hr.prisma`) avait déjà `EmploymentContract`/`LeaveRequest`/`EmployeeAttendance` sans API pour les piloter — même situation que `MessageTemplate` avant sa tranche §31. Cette tranche ferme §27 dans son intégralité, dans [employees](../apps/api/src/modules/employees/) :

- **Contrats** (`EmploymentContract`, `contract.service.ts`) : `POST/GET /employees/:employeeId/contracts`, `PATCH .../contracts/:id`. Listés du plus ancien au plus récent — sert aussi d'historique professionnel (renouvellements, changements de type) sans dupliquer cette vue dans un endpoint séparé. **Nouvelle permission `hr.salary.manage`**, distincte de `hr.manage` et accordée aux mêmes rôles pour l'instant (`SCHOOL_OWNER`, `HR_MANAGER`) mais vérifiée séparément côté route — « les informations salariales doivent avoir des permissions particulièrement restrictives » (§27) est pris au pied de la lettre : un rôle qui n'aurait un jour que `hr.manage` (fiche, présences, congés) resterait bloqué sur les contrats sans changement de code. La fiche générale du personnel (`GET /employees`) ne joint toujours aucune donnée salariale.
- **Présences et retards** (`EmployeeAttendance`, `staff-attendance.service.ts`) : `POST/GET /employees/:employeeId/attendance`. Upsert natif sur `@@unique([employeeId, date])` — contrairement à `Attendance` (élèves), aucune colonne nullable dans cette contrainte, donc pas le piège NULL documenté sur `recordRollCall`. `EmployeeAttendanceStatus.LATE` couvre les retards, pas de modèle séparé.
- **Congés** (`LeaveRequest`, `leave-request.service.ts`) : `POST/GET /employees/:employeeId/leave-requests`, `PATCH .../leave-requests/:id/decision` (`APPROVED`/`REJECTED`/`CANCELLED`). `PENDING` est le seul statut décidable — une décision déjà prise reste définitive (409 `LEAVE_REQUEST_ALREADY_DECIDED`). `approvedByEmployeeId` résolu côté serveur depuis l'acteur authentifié, jamais un id fourni par le client (même garde que `discipline`/`attendance` élèves).
- **Évaluations** (nouveau modèle `PerformanceEvaluation`) : `POST/GET /employees/:employeeId/evaluations`. Pas d'échelle imposée — §27 n'en fixe aucune — `score` reste un entier libre, l'établissement choisit sa propre convention.
- **Documents personnel** (nouveau modèle `EmployeeDocument`, même forme que `StudentDocument`) : `POST/GET /employees/:employeeId/documents`, `DELETE .../documents/:id` (suppression douce). Métadonnées seulement, le fichier est déjà téléversé ailleurs.
- **Charges horaires** (`GET /employees/:id/workload?academicYearId=`) : agrège `TeacherAssignment.hoursPerWeek` (§20, déjà modélisé) pour un employé — pas de nouveau modèle, juste l'agrégat qu'aucun endpoint n'exposait encore. Un employé sans affectation (personnel non enseignant) obtient `0`, pas une erreur.
- **Export de paie** (`payroll-export.service.ts`, `hr.salary.manage`) : `GET /employees/payroll/export.csv`, même bibliothèque `lib/csv.ts` que les autres exports CSV du code. Une ligne par employé actif (non archivé, non `TERMINATED`) avec son contrat **actif** (`startDate <= aujourd'hui <= endDate` ou `endDate` nul) — un employé sans contrat actif apparaît quand même avec des champs salaire vides plutôt qu'omis silencieusement.

**Restent hors périmètre** : export PDF de paie (CSV seul pour cette tranche), self-service employé (demander son propre congé) — ce module reste piloté par le personnel RH/direction, aucun portail employé n'existe dans ce code.

**Correctif (audit de couverture complet §1-§41) — un employé licencié gardait sa capacité d'agir sous son ancienne identité de personnel** : `archiveEmployee` pose `deletedAt`/`status: "TERMINATED"` sur `Employee`, mais `resolveActingEmployeeId` — dupliqué à l'identique dans dix services (`attendance`, `discipline`, `elearning`, `leave-request`, `performance-evaluation`, `cash-session`, `expense`, `student-payment`, `grade`, `homework`, `library`) — résolvait `Employee` par `userId` seul, sans filtrer `deletedAt`. Même classe de bug que `Tenant.status = SUSPENDED` jamais consulté par `enforceTenantScope` (voir plus haut) : un signal de retrait que le service écrit mais qu'aucune garde ne lit. Concrètement, un `SCHOOL_OWNER`/`ACCOUNTANT` licencié pour détournement de fonds (§27) gardait, tant que personne ne pensait séparément à révoquer son `UserRole` via `tenant-users`, la capacité d'encaisser des paiements, ouvrir/fermer la caisse, saisir des notes ou traiter des présences sous son identité `Employee` désormais rétractée — polluant la piste d'audit financière (§23/§33) d'une fausse légitimité. Fermé en extrayant l'unique définition correcte dans [lib/acting-employee.ts](../apps/api/src/lib/acting-employee.ts) (filtre sur `deletedAt: null`, jamais sur `status` — un employé `ON_LEAVE` reste un employé légitime, temporairement absent, pas retiré), consommée par les dix services plutôt que dupliquée une onzième fois. Testé dans [finance-payments.test.ts](../apps/api/src/test/integration/finance-payments.test.ts) : un encaissement réussit, l'employé est archivé, le même utilisateur (même session, même permission `finance.write`) se voit refuser un second encaissement (`403 EMPLOYEE_RECORD_REQUIRED`), exactement comme s'il n'avait jamais eu de fiche personnel.

## Administration académique — §20 clôturé (Phase 6 démarrée)

Le §20 (« module administration académique ») listait années/périodes/cycles/niveaux/classes/départements/matières (couverts en Phase 5, voir ci-dessus) plus programmes, coefficients, affectations des enseignants, emplois du temps — ces quatre derniers ajoutés après la clôture de la Phase 5, toujours dans [school-config](../apps/api/src/modules/school-config/) :

- **Affectations des enseignants** (`TeacherAssignment`) : lie employé/matière/classe/année scolaire, avec vérification d'existence des quatre références, garde-fou classe↔année (une classe n'appartient qu'à une année, l'affectation doit être cohérente) et unicité (un même quadruplet ne peut être affecté deux fois).
- **Emplois du temps** (`Timetable`/`TimetableEntry`) : une grille par classe et par année, chaque entrée (matière, enseignant, jour, créneau `HH:MM`, salle en texte libre) validée sur deux axes de conflit indépendants — la classe ne peut avoir deux cours au même créneau, et l'enseignant ne peut être dans deux classes en même temps, ce dernier vérifié sur **toutes** les grilles de la même année scolaire (pas seulement celle en cours d'édition).
- **Programmes** (`Program`) : référentiel simple code/nom, rattachable optionnellement à un niveau, réutilisé par `Classroom.programId`.
- **Coefficients** (`SubjectCoefficient`) : un coefficient par couple matière/niveau (`upsert` — renvoyer un coefficient déjà défini le met à jour plutôt que de lever un conflit), consommé plus tard par le calcul des moyennes (§21, Phase 6).

`Program` et `SubjectCoefficient` existaient dans le schéma depuis la Phase 5 sans service pour les piloter ; c'est maintenant fait, §20 est donc intégralement couvert. Restent hors périmètre : salles comme entité propre (le `roomLabel` de `TimetableEntry` reste une chaîne libre, pas de modèle `Room`/réservation), calendriers/jours fériés dédiés (`AcademicPeriod` couvre le découpage trimestre/semestre, pas un calendrier d'événements).

## Notes et évaluations — §21 clôturé pour le périmètre retenu

Module [grading](../apps/api/src/modules/grading/), monté sur `/api/v1/grading`, même chaîne d'autorisation que les autres (`requireAuth + enforceTenantScope + requireTenantMembership + requirePermission`). Trois permissions dédiées existaient déjà dans le seed sans module pour les consommer (`grades.read`, `grades.write`, `grades.publish` — `TEACHER` a lecture+écriture mais pas publication ; `SCHOOL_OWNER`/`DIRECTOR`/`ACADEMIC_DIRECTOR` ont publication).

- **Types d'évaluation** (`AssessmentType`) : référentiel code/nom (DEVOIR, EXAMEN…), derrière `tenant.settings.manage` comme les autres tables de configuration.
- **Évaluations** (`Assessment`) : matière + classe + type + période, `maxScore`/`coefficient` propres à chaque évaluation (une interrogation peut être notée sur 10 avec un coefficient différent d'un examen sur 20). Créée/modifiée derrière `grades.write` ; garde-fou classe↔période (même année scolaire, même principe que `TeacherAssignment`/`Timetable` en §20). Modification bloquée après publication (`ASSESSMENT_ALREADY_PUBLISHED`).
- **Saisie des notes** (`Grade`) : `PUT /assessments/:id/grades` accepte un tableau `{studentId, score|isAbsent, comment}`, upsert par élève (contrainte unique `assessmentId+studentId`), refusé une fois l'évaluation publiée (`ASSESSMENT_LOCKED`) — utiliser la correction ci-dessous à la place. Note plafonnée à `maxScore` (`SCORE_EXCEEDS_MAX`). `enteredByEmployeeId` résolu côté serveur depuis le token (`Employee.userId` = appelant), jamais depuis le corps de la requête, même principe que `uploadedByUserId` sur les documents élèves (§19).
- **Publication et verrouillage** (`POST /assessments/:id/publish`, derrière `grades.publish`) : marque l'évaluation publiée et verrouille (`isLocked=true`) toutes ses notes déjà saisies en une seule fois — implémentation choisie pour ce verrouillage : au niveau de l'évaluation plutôt qu'au niveau du bulletin (le commentaire du schéma Prisma évoquait la publication du bulletin ; la génération du bulletin, voir ci-dessous, ne dépend délibérément pas de cette publication — les deux verrous restent indépendants).
- **Corrections autorisées** (`PATCH /grades/:id/correct`, derrière `grades.publish` — plus restrictif que la saisie normale) : fonctionne que la note soit verrouillée ou non, toujours journalisé dans `GradeChangeLog` (score précédent, score nouveau, auteur, motif obligatoire) — jamais d'écrasement silencieux.
- **Moyennes, classement et bulletins** (`ReportCard`/`ReportCardItem`, `POST /report-cards/generate` derrière `grades.publish`) : génère (ou régénère) en une seule fois les bulletins de **toute une classe** pour une période — jamais élève par élève, car le rang de classe n'a de sens que calculé ensemble. Pour chaque élève inscrit (`Enrollment` ENROLLED/RE_ENROLLED de la classe/année) : moyenne par matière = notes normalisées sur 20 (`score/maxScore*20`) pondérées par le coefficient propre de chaque évaluation, notes marquées absentes exclues du calcul (pas comptées comme zéro — choix MVP, voir limite ci-dessous) ; moyenne générale = moyennes par matière pondérées par `SubjectCoefficient` (le niveau scolaire vient de `Enrollment.gradeLevelId`, coefficient par défaut 1 si non défini) ; rang de classe = tri décroissant par moyenne générale (classement standard « compétition », ex-æquo partagent le même rang) ; mention = seuils fixes `>=16 Très bien / >=14 Bien / >=12 Assez bien / >=10 Passable` sinon aucune. `GET /report-cards` (filtrable par classe/période/élève), `GET /report-cards/:id` (avec le détail par matière), `GET /report-cards/:id/pdf` (bulletin PDF généré à la volée avec `pdfkit`, même approche que la carte scolaire du §19 — pas de stockage, `pdfUrl` reste `null`).

**Limites assumées pour ce périmètre** : système de notation non configurable par tenant (échelle /20, arrondi à 2 décimales, seuil de réussite et mentions fixes — suppose un service `TenantSetting` qui n'existe pas encore, même blocage que la détection de doublons configurable en §19) ; une absence non justifiée n'est pas comptée comme zéro dans la moyenne (à trancher côté produit — actuellement neutre plutôt que pénalisant) ; procès-verbaux et conseils de classe différés au-delà du MVP ; relevé de notes traité comme le même artefact que le bulletin (pas de mise en page distincte).

**Correctif (audit de couverture complet §1-§41)** : `Grade.studentId` et `ReportCard.studentId` étaient en `onDelete: Cascade` — une suppression dure d'un dossier élève (aucune route ne le fait aujourd'hui, seul `POST /students/:id/archive` existe) effacerait silencieusement son historique de notes et bulletins avec lui, à l'opposé de la suppression logique demandée par §40. Passé à `RESTRICT` (onDelete omis, comportement par défaut de Prisma pour une relation requise — même convention déjà utilisée pour `StudentBedAssignment`) : une tentative de suppression dure échoue tant que des notes ou bulletins existent, plutôt que de les emporter en silence. Prouvé par un nouveau cas dans [grading.test.ts](../apps/api/src/test/integration/grading.test.ts) et [report-cards.test.ts](../apps/api/src/test/integration/report-cards.test.ts) : `testAdminPrisma.student.delete(...)` échoue et la ligne survit.

## Présences et discipline — §22 clôturé pour le périmètre retenu, Phase 6 terminée

Deux modules distincts (schéma déjà prêt depuis la Phase 2/5 : `Attendance`, `DisciplinaryIncident` dans `student.prisma`), chacun avec ses propres permissions (`attendance.read`/`attendance.write`, `discipline.read`/`discipline.write` — ajoutées au seed avec cette tranche, §22 demandait explicitement des « droits d'accès spécifiques »). `TEACHER`/`SUPERVISOR` ont les deux en lecture+écriture ; `DIRECTOR` gère la discipline mais pas les présences au jour le jour ; `SCHOOL_OWNER`/`SCHOOL_ADMIN`/`ACADEMIC_DIRECTOR`/`TENANT_AUDITOR` ont uniquement la lecture, cohérent avec le reste du RBAC (l'établissement supervise, le personnel de terrain saisit).

- **Présences** ([attendance](../apps/api/src/modules/attendance/), monté sur `/api/v1/attendance`) : `PUT /roll-call` (appel par classe) accepte `{classroomId, date, subjectId?, entries: [{studentId, status, justificationNote?}]}`, `status` ∈ `PRESENT/ABSENT/LATE/EXCUSED`. Implémenté en `findFirst` + create/update plutôt qu'un `upsert` Prisma natif : la contrainte unique `(studentId, classroomId, subjectId, date)` a `subjectId` nullable, et Postgres traite deux `NULL` comme distincts pour l'unicité — un `upsert` natif ne détecterait donc jamais de conflit pour un appel journalier sans matière (`subjectId` omis) et créerait un doublon silencieux à chaque nouvel appel du même jour. `PATCH /:id/justify` ne fonctionne que sur un enregistrement `ABSENT` (`NOT_AN_ABSENCE` sinon), bascule le statut à `EXCUSED` et enregistre `justificationNote`. `recordedByEmployeeId` résolu côté serveur depuis le token, même principe que `enteredByEmployeeId` en §21.
- **Discipline** ([discipline](../apps/api/src/modules/discipline/), monté sur `/api/v1/discipline`) : `POST /incidents` (sévérité `MINOR/MODERATE/SEVERE`, sanction et mesure corrective en texte libre), `PATCH /incidents/:id`, suppression douce (`deletedAt`). `GET /students/:studentId/history` couvre l'« historique disciplinaire » du §22 — tous les incidents non supprimés d'un élève, plus récents d'abord. `reportedByEmployeeId` résolu côté serveur, même principe.

**Restent hors périmètre** : justificatif comme pièce jointe (`justificationNote` reste du texte libre ; un vrai fichier réutiliserait `StudentDocument` du §19, pas dupliqué ici) ; règles d'escalade automatique des sanctions. La notification effective des parents était listée ici comme reportée (suppose §28 + §8, tous deux Phase 8, non construits) — voir les sections « Rattachement parent-élève » et « Notifications aux parents » plus bas, désormais faite dans son périmètre minimal (canal IN_APP uniquement).

Avec §20, §21 et §22 clos pour leur périmètre retenu, **la Phase 6 (Gestion académique) est terminée**.

## Module financier de l'établissement — §23 démarré (Phase 7), frais, factures, encaissement, dépenses et caisse faits

§23 est la plus grosse section du cahier des charges (catégories de frais, grilles tarifaires, factures, paiements complets/partiels, remises/bourses/exonérations/pénalités, reçus numérotés, annulations contrôlées, remboursements, caisse, clôtures journalières, dépenses, fournisseurs, situation financière d'un élève, impayés, rapports, export PDF/Excel) — traitée en tranches plutôt qu'en un seul morceau, comme la Phase 6. Cette tranche couvre la base : catégories/grilles tarifaires et cycle de vie de la facture, **sans encore l'encaissement** (paiements, reçus, remboursements — tranche suivante). Le schéma (`finance.prisma`, Phase 2/5) a déjà tous les modèles nécessaires pour l'ensemble du §23 ; seul le service manquait, même situation que `Program`/`SubjectCoefficient` avant leur tranche dédiée en §20.

Nouveau module [finance](../apps/api/src/modules/finance/), monté sur `/api/v1/finance`, derrière `finance.read`/`finance.write` (permissions déjà présentes dans le seed depuis la Phase 3, mais jusqu'ici seulement consommées par le module `payments` — inchangé). Toutes les sommes en centimes (`Int`), jamais en flottant (§23, §40).

- **Catégories de frais** (`FeeCategory`) et **grilles tarifaires** (`FeeStructure` : année scolaire + niveau optionnel + catégorie + montant + échéance + obligatoire ou non) : référentiel classique, code unique par tenant, mêmes garde-fous d'existence croisée que le reste de `school-config`.
- **Factures élève** (`StudentInvoice`/`StudentInvoiceItem`) : `POST /student-invoices` crée une facture `DRAFT` avec ses lignes en une seule écriture Prisma imbriquée (atomique nativement, pas besoin de `$transaction` explicite ici). Chaque ligne référence optionnellement une `FeeStructure` (traçabilité) mais peut aussi être libre (ex. frais d'inscription hors grille). `discountCents` par ligne couvre remises/bourses/exonérations (une exonération totale = `discountCents == amountCents`) — refusé si le rabais dépasse le montant de la ligne. `totalCents` calculé serveur (jamais fourni par le client) en centimes entiers. Numérotation via `generateReference("INV")` (réutilisé tel quel depuis [payments/reference.ts](../apps/api/src/modules/payments/reference.ts), déjà pensé pour ce rôle).
- **Cycle de vie** : `DRAFT → ISSUED` (`POST /:id/issue`, une seule fois) → `CANCELLED` (`POST /:id/cancel`, « annulation contrôlée » : refusée si `paidCents > 0` ou statut déjà `PAID`/`PARTIALLY_PAID` — il faudrait rembourser d'abord, hors périmètre de cette tranche). Le schéma n'a pas de colonne pour un motif d'annulation ; l'annulation reste donc gardée par la règle métier seule, pas par une piste d'audit texte — limite assumée plutôt qu'un ajout de colonne hors sujet pour cette tranche.

## Encaissement et reçus — §23 tranche 2

**Espèces uniquement pour cette tranche** — le seul canal réellement câblé de bout en bout à ce jour, même situation que le flux SaaS de la Phase 3 (Mobile Money : adaptateur de référence présent, aucun opérateur réellement enregistré). Un paiement électronique de frais scolaires réutiliserait le pipeline `PaymentIntent`/`PaymentTransaction` existant via son champ `studentInvoiceId` déjà prévu depuis le §24 — non branché ici, tranche suivante.

- **`POST /finance/student-invoices/:id/payments`** (toujours [finance](../apps/api/src/modules/finance/), `finance.write`) : encaissement complet ou partiel. Refusé si la facture est `DRAFT` (`INVOICE_NOT_ISSUED` — il faut d'abord émettre), `CANCELLED`, déjà `PAID`, ou si le montant dépasse le solde restant (`AMOUNT_EXCEEDS_BALANCE`, jamais de trop-perçu silencieux). `recordedByEmployeeId` **obligatoire** (le commentaire du schéma le dit explicitement pour un encaissement espèces) — résolu depuis le token vers l'`Employee` lié (`Employee.userId`), refusé avec `EMPLOYEE_RECORD_REQUIRED` si l'appelant n'a pas de fiche personnel liée, même s'il a la permission `finance.write` (un propriétaire d'établissement sans fiche RH ne peut pas encaisser directement).
- **Transaction unique** (`withTenantSession`, §23 : « utiliser des transactions pour les opérations financières ») : création du `StudentPayment`, mise à jour de `StudentInvoice.paidCents`/`status` (`ISSUED`/`PARTIALLY_PAID` → `PARTIALLY_PAID` ou `PAID` selon le solde), création du `StudentReceipt` numéroté (`generateReference("REC")`) — les trois dans la même transaction Postgres, jamais un encaissement enregistré sans reçu ou un solde désynchronisé.
- **Reçus** : `GET /finance/receipts/:id` (métadonnées), `GET /finance/receipts/:id/pdf` (PDF généré à la volée avec `pdfkit`, même approche que la carte scolaire et le bulletin — pas de stockage, `pdfUrl` reste `null`).
- **Annulation contrôlée** (`POST /student-invoices/:id/cancel`, tranche précédente) refuse désormais aussi toute facture avec au moins un paiement enregistré (`INVOICE_HAS_PAYMENTS`) — cohérent avec la garde déjà posée sur `paidCents`.

**Restent hors périmètre** (prochaines tranches, au moment de la tranche 2) : remboursements (aucun modèle pour un remboursement en espèces — `RefundTransaction` n'existe que côté paiement électronique, rattaché à `PaymentTransaction` ; un remboursement espèces nécessiterait une décision de schéma, différée plutôt que bricolée dans cette tranche), paiements électroniques pour les frais scolaires, situation financière consolidée d'un élève, impayés, génération automatique de factures en masse depuis une grille tarifaire. Rapports de recettes/dépenses et export PDF/CSV sont désormais faits — voir la section dédiée plus bas.

## Dépenses et caisse — §23 tranche 3

- **Catégories de dépenses** (`ExpenseCategory`) et **dépenses** (`Expense`) : même référentiel classique que les catégories de frais (code unique par tenant, `EXPENSE_CATEGORY_CODE_TAKEN`). `Expense` référence une catégorie obligatoire, `supplierName` reste une chaîne libre (pas d'entité `Supplier` dédiée, même choix que documenté en tranche 2). Suppression douce (`deletedAt`), filtrable par catégorie et plage de dates (`GET /expenses?categoryId=&startDate=&endDate=`). `approvedByEmployeeId` résolu au mieux depuis `Employee.userId` (contrairement à `StudentPayment.recordedByEmployeeId`, le schéma ne le rend pas obligatoire — une dépense peut être créée sans fiche employé liée).
- **Caisse** (`CashSession`) : `POST /cash-sessions/open` ouvre une session avec un solde d'ouverture ; une seule session `OPEN` à la fois par périmètre (`campusId` s'il existe, sinon tout le tenant — `campusId` `null` est son propre compartiment), refusé sinon (`CASH_SESSION_ALREADY_OPEN`). `POST /cash-sessions/:id/close` la clôture avec un solde de clôture saisi manuellement, refusé si déjà fermée (`CASH_SESSION_ALREADY_CLOSED`). Contrairement à l'encaissement (§23 tranche 2), ouvrir/fermer une caisse **exige** une fiche `Employee` liée à l'utilisateur (`EMPLOYEE_RECORD_REQUIRED`), même garde-fou que `StudentPayment`.
- **Limite assumée** : le solde de clôture est saisi par le personnel, pas calculé — `StudentPayment`/`Expense` ne portent pas de `cashSessionId` (le schéma ne prévoit pas ce rattachement), donc aucun rapprochement automatique entre encaissements/dépenses de la période et le comptage en caisse. Un écart éventuel reste une vérification manuelle hors de cette API, pas un contrôle applicatif.

**Restent hors périmètre** (prochaines tranches) : paiements électroniques pour les frais scolaires, rattachement `CashSession` aux encaissements/dépenses pour un rapprochement automatique, génération automatique de factures en masse depuis une grille tarifaire. Remboursements, situation financière consolidée, et rapports de recettes/dépenses avec export PDF/CSV sont désormais faits — voir les sections dédiées ci-dessous.

## Remboursements et situation financière consolidée — §23 tranche 4

Nouveau modèle `StudentPaymentRefund` (`prisma/schema/finance.prisma`, migration `20260812141421_add_student_payment_refund` — RLS activée dans la même migration, même motif que toutes les tables tenant-scoped depuis Phase 2) : append-only, un paiement peut être remboursé partiellement plusieurs fois. `RefundTransaction` (schéma Phase 2) restait structurellement lié à `PaymentTransaction` électronique (FK obligatoire) — inutilisable pour un remboursement espèces sans modifier ce modèle-là ; un modèle dédié était la décision de schéma jusque-là différée.

- **`POST /finance/payments/:paymentId/refunds`** (`finance.write`, [student-payment.service.ts](../apps/api/src/modules/finance/student-payment.service.ts)) : plafonné à `payment.amountCents - somme(refunds existants)` (`REFUND_EXCEEDS_PAYMENT` sinon), exige un `Employee` lié (`EMPLOYEE_RECORD_REQUIRED`, même garde-fou que `recordCashPayment`). Transaction unique (`withTenantSession`) : crée le remboursement, décrémente `StudentInvoice.paidCents`, recalcule le statut (`0 → ISSUED`, sinon `PARTIALLY_PAID`). `GET /finance/payments/:paymentId/refunds` liste l'historique. Une facture `CANCELLED` ne peut structurellement avoir de solde remboursable (garanti par `cancelStudentInvoice`), donc aucune garde spécifique n'était nécessaire pour ce cas.
- Ça débloque exactement ce que `cancelStudentInvoice` annonçait depuis la tranche 1 (« il faudrait rembourser d'abord ») : un remboursement intégral ramène `paidCents` à 0, et l'annulation redevient possible.
- **`GET /finance/students/:studentId/financial-situation`** ([financial-situation.service.ts](../apps/api/src/modules/finance/financial-situation.service.ts)) : total facturé/payé/solde restant sur les factures non annulées, plus la liste des impayés — dérivée à la volée (`status ∈ {ISSUED, PARTIALLY_PAID} AND dueAt < now`), pas depuis le statut `OVERDUE` de l'enum, qui reste non piloté (aucun job planifié ajouté, cohérent avec le reste du périmètre minimal du module).

## Rapports de recettes/dépenses et exports PDF/CSV — §23 tranche 5

Ferme le dernier point resté hors périmètre depuis les tranches 2/3 (« rapports de recettes/dépenses, export PDF/Excel »). [financial-report.service.ts](../apps/api/src/modules/finance/financial-report.service.ts) : `GET /finance/reports/revenue` et `GET /finance/reports/expenses` (`finance.read`, `?startDate=&endDate=` obligatoires, `endDate < startDate` rejeté par zod `.refine()`), chacun avec une variante `/csv` et `/pdf` (même service d'agrégation, trois formats de sortie). Agrégation en mémoire (même style que `stats-admin.service.ts`, §31 tranche 9) plutôt qu'un `GROUP BY` SQL — le volume par tenant/période ne le justifie pas.

- **Recettes** (`StudentPayment` sur `paidAt`, `StudentPaymentRefund` sur `refundedAt`) : total encaissé, total remboursé, net, répartition par mode de paiement et par jour. Un remboursement compte sur sa **propre** date, jamais sur celle du paiement d'origine — cohérence comptable période par période, une période déjà close n'est jamais retouchée par un remboursement ultérieur.
- **Dépenses** (`Expense` sur `expenseDate`, `deletedAt: null`) : total dépensé, répartition par catégorie et par jour.
- **Export Excel explicitement écarté** : même décision que l'export élèves (§19/Phase 5) — un CSV s'ouvre nativement dans Excel, générer un vrai `.xlsx` introduirait une dépendance (`exceljs`/`xlsx`) pour un besoin déjà couvert. `lib/csv.ts` est extrait de `import-export.service.ts` (§19) à cette occasion — `escapeCsvField` (garde anti-injection de formule) et `buildCsv` sont désormais partagés entre les deux exports CSV du projet plutôt que dupliqués.
- **PDF** ([financial-report-pdf.service.ts](../apps/api/src/modules/finance/financial-report-pdf.service.ts)) : même convention que `receipt-pdf.service.ts` (pdfkit, bufferisé en mémoire via `chunks`/`Buffer.concat`, jamais stocké). Ne couvre pas encore les exigences générales de §30 (logo, QR code de vérification, historique de génération) — aucun générateur PDF existant dans ce code ne les couvre non plus, gap transversal plutôt que spécifique à cette tranche.

## Rattachement parent-élève par invitation — §8 (Phase 8 démarrée)

Le schéma (`family.prisma`, Phase 2) avait déjà tous les modèles nécessaires — `ActivationInvitation`, `ActivationCode`, `ParentStudentRelationship`, `StudentUserLink`, `FamilyAccount`/`Guardian`/`FamilyMember` — et le middleware `requireVerifiedStudentRelationship` était déjà écrit et testé isolément, mais aucun n'était raccroché à une route réelle. Cette tranche construit le module [family](../apps/api/src/modules/family/) (`/api/v1/family`) qui les active, dans le périmètre strict qui débloquait les deux trous documentés en Phase 5/§22 : rattachement lui-même et notification (§28 ci-dessous). `FamilyAccount`/`Guardian`/`FamilyMember` restent non touchés — `ParentStudentRelationship` référence `parentUserId` brut, l'abonnement familial en libre-service (§9) reste une tranche à part.

- **Invitation** (`POST /family/invitations`, `students.write` réutilisé — pas de nouvelle permission, même précédent que les sous-fonctionnalités finance) : le personnel crée une `ActivationInvitation` pour un élève + catégorie (`PARENT`/`STUDENT`) + email et/ou téléphone du bénéficiaire. Un `ActivationCode` court (10 caractères, alphabet sans `0/O/1/I`, généré par [`activation-code.ts`](../apps/api/src/lib/activation-code.ts) sur le même principe que `refresh-token.ts` : plaintext rendu une fois, seul le hash SHA-256 persisté) est renvoyé **en clair dans la réponse HTTP**. Aucun canal email/SMS réel n'est câblé nulle part dans ce code (même limite que Mobile Money, §24) : le personnel le transmet manuellement pour cette tranche.
- **Rédemption** (`POST /family/activation/redeem`, `requireAuth` seul — le bénéficiaire n'est membre d'aucun tenant du côté de l'élève au moment de l'appel) : vérifie code non expiré/non révoqué/non utilisé, invitation active, et une vérification d'identité légère (§8 point 4) — l'email ou le téléphone de l'invitation doit correspondre au compte appelant. Rédemption réussie → `PARENT` crée/réactive une `ParentStudentRelationship` `VERIFIED` ; `STUDENT` crée un `StudentUserLink`. Le tout dans une seule transaction via `withTenantSession(invitation.tenantId, …)`, code marqué utilisé par un `updateMany` conditionné sur `usedAt: null` (compare-and-swap, empêche une double rédemption concurrente).
- **Révocation** : `POST /family/invitations/:id/revoke` (invitation non utilisée) et `POST /family/relationships/:id/revoke` (relation vérifiée, motif obligatoire — `revokedReason`, déjà au schéma pour §9 : « les établissements doivent pouvoir révoquer une relation incorrecte »). Les deux écrivent désormais un `AuditLog` (finalisation Phase 2, voir section dédiée plus haut) — `activation_invitation.revoke` / `parent_student_relationship.revoke`.
- **`GET /family/children`** (`requireAuth` seul) : le parent consulte ses enfants vérifiés, potentiellement dans des tenants différents (§9) — lecture cross-tenant assumée, même raisonnement que `requireVerifiedStudentRelationship`.
- **Correction RLS nécessaire** : `ActivationInvitation` avait une politique RLS (Phase 2) qui bloquait sa propre lecture bootstrap (`redeemActivation` résout le tenant DEPUIS le code, avant tout contexte tenant établi — impossible tant que `app.tenant_id` doit déjà être positionné). Migration `20260812090000_activation_invitation_no_rls`, même correctif que `TenantDomain`/`ParentStudentRelationship` en Phase 2 (`..._tenant_domain_no_rls`, `..._parent_student_relationship_no_rls`) : `DISABLE ROW LEVEL SECURITY` sur cette table précisément, avec la même justification (lecture ponctuelle par clé, jamais un scan, sur un identifiant que l'appelant possède déjà). `Student`, lui, garde sa RLS — `listVerifiedChildrenForParent` lit chaque élève via `withTenantSession(relationship.tenantId, …)` plutôt que par une dérogation RLS supplémentaire, la donnée étant plus sensible qu'une simple table de routage.

**Restent hors périmètre** : portail parent complet (§25), changement d'établissement d'un élève lié (§10). Abonnement familial en libre-service (§9) est désormais fait — voir la section dédiée ci-dessous.

**Lacune identifiée (audit de couverture complet §1-§41), non traitée ici** : §16 demande explicitement « pour les élèves mineurs, prévoir les règles de consentement et de validation du parent ou tuteur selon les paramètres applicables » pour l'abonnement individuel de l'élève. Ni la rédemption d'un code d'activation `STUDENT` ni le pipeline `/subscriptions/student/:studentId/...` (§26) ne consultent `Student.dateOfBirth` ou n'imposent de validation parentale — un élève mineur peut aujourd'hui créer et payer son propre abonnement sans qu'aucun parent/tuteur n'en soit informé. Contrairement aux autres lacunes de ce type déjà documentées (détection de doublons configurable, système de notation configurable), celle-ci n'est bloquée par aucune brique de configuration absente (`TenantSetting`) — mais le mécanisme concret attendu (seuil d'âge ? notification simple ou blocage total ? consentement explicite du parent déjà lié via `ParentStudentRelationship` ?) est une décision produit, pas un correctif de sécurité ponctuel comme les autres points de cette liste.

## Abonnement familial en libre-service — §9

§9 a deux volets, bien distincts en pratique : les règles d'isolation/révocation/audit inter-tenant (déjà satisfaites par §8/§18/§25 — `runWithContext` par enfant dans `getParentDashboard`, révocation avec motif obligatoire) et « un abonnement familial doit définir le nombre maximum d'enfants couverts », qui restait le seul point non construit — `FamilyAccount`/`Guardian`/`FamilyMember` existaient au schéma (Phase 2) sans aucun code applicatif.

- **`POST/GET/PATCH /family/family-account`** ([family-account.service.ts](../apps/api/src/modules/family/family-account.service.ts)) : `requireAuth` seul, même bloc bénéficiaire que le reste de `family.routes.ts` — le parent n'est membre d'aucun tenant. La création résout ou crée un `Guardian` lié à l'utilisateur (à partir de son profil déjà renseigné), puis crée `FamilyAccount` + `FamilyMember` (`PRIMARY`) en une transaction. Refusé (409 `FAMILY_ACCOUNT_ALREADY_EXISTS`) si un compte existe déjà — un parent n'a qu'un seul `FamilyAccount`. Seul le titulaire principal peut ajuster `maxChildren` par `PATCH`.
- **Plafond appliqué à la rédemption** (`activation-invitation.service.ts`, `redeemActivation`) : avant de vérifier une nouvelle relation `PARENT`, compte les `ParentStudentRelationship` déjà `VERIFIED` du parent (tous tenants confondus — `ParentStudentRelationship` n'a pas de RLS, le `count()` n'est donc pas limité au tenant verrouillé par la session en cours) et refuse (409 `FAMILY_CHILD_LIMIT_REACHED`) si l'ajout dépasserait `FamilyAccount.maxChildren`. Aucun plafond si le parent n'a pas encore de `FamilyAccount`, ou si `maxChildren` est resté `null` (illimité) — jamais un plafond implicite.
- **`POST/GET /subscriptions/family`, `.../invoice`, `.../payment-intent`, `.../cash-payment`, `.../:id/cancel`** ([subscription.controller.ts](../apps/api/src/modules/subscriptions/subscription.controller.ts)) : pipeline strictement symétrique au flux `/subscriptions/school` déjà existant (`createDraftSubscription` → `createInvoiceForSubscription` → `createPaymentIntent` → `recordManualCashPayment`), résolu par `familyAccountId` plutôt que `tenantId`, jamais `enforceTenantScope`. `createDraftSubscription`/`findSubscriptionForOwner` acceptaient déjà génériquement `ownerType: "PARENT"` — rien à changer côté `subscription.service.ts`. **Limite héritée, pas nouvelle** : comme pour `/subscriptions/school`, aucune route self-service ne fait transitionner `DRAFT → PENDING_PAYMENT` (`subscription-transitions.ts` l'exige avant `ACTIVE`) — seuls les tests appellent `transitionSubscription` directement ; un vrai parcours de paiement électronique bouclerait cette transition lors de la création du `PaymentIntent`, à faire en même temps que le reste du pipeline SaaS (§24).
- **`GET /parent-portal/dashboard`** (§18) expose désormais `subscription` (`null` si le parent n'a pas encore de `FamilyAccount`, jamais un abonnement fabriqué) — la réponse est passée d'un tableau brut à `{children, subscription}`.

**Restent hors périmètre** : ajout d'un `CO_GUARDIAN` au foyer (le schéma le permet, `FamilyMember.roleInFamily`, mais aucune route ne l'expose), paiement électronique réel (même limite que §24 partout ailleurs dans ce code).

## Notifications aux parents — §28 tranche 1 (minimal, débloque le trou du §22)

Module [communication](../apps/api/src/modules/communication/) (`/api/v1/communication`), strictement dimensionné pour clore le trou documenté en §22 (« notification effective des parents ») — pas le §28 complet.

- **`notifyParentsOfStudent`** ([notification.service.ts](../apps/api/src/modules/communication/notification.service.ts)) : trouve les `ParentStudentRelationship` `VERIFIED` d'un élève, crée une `Notification` par parent (**canal `IN_APP`, source de vérité, jamais désactivable, jamais habillée par un `MessageTemplate`**), puis envoie en plus une copie email à chaque parent qui n'a pas désactivé la catégorie (`input.type`, ex. `"attendance.absence"`, `"discipline.incident"`) via `sendEmail` (voir « Canaux de notification réels » ci-dessous) — les deux coexistent, jamais un remplacement de l'IN_APP. Silencieux (pas d'erreur) si l'élève n'a aucun parent vérifié.
- **Câblage** : `attendance.service.ts:recordRollCall` (une entrée `ABSENT`) et `discipline.service.ts:createIncident` (tout incident créé) appellent `notifyParentsOfStudent` après l'écriture.
- **Consultation** (`requireAuth` seul, scopé sur `req.user.id` — `Notification` n'est pas un modèle tenant-scoped, un parent peut avoir des notifications de plusieurs établissements) : `GET /communication/notifications` (filtrable `?unreadOnly=true`), `PATCH /communication/notifications/:id/read`.
- **Préférences par canal** (`NotificationPreference`, même absence de scope tenant) : `GET /communication/notification-preferences` (lignes explicitement écrites par l'utilisateur seulement — l'absence d'une `(channel, category)` veut dire "activé par défaut", jamais matérialisée), `PUT /communication/notification-preferences/:channel/:category` (`{isEnabled}`, upsert par clé composite comme `PlatformSetting`, §31 tranche 10). **`channel` restreint à `EMAIL` par validation zod** (400 sinon) : IN_APP n'est jamais désactivable (source de vérité ci-dessus) et aucun appelant n'envoie encore de SMS/PUSH pour ces catégories — les accepter créerait un réglage qui ne changerait jamais rien, jamais fait dans ce code.
- **Consommation de `MessageTemplate` (`resolveMessageTemplate`, `renderTemplateBody`)** : avant d'envoyer la copie email, cherche un `MessageTemplate` `channel: EMAIL` dont le `code` égale `input.type` — modèle propre au tenant courant en priorité (`@@unique([tenantId, code])`, même piège NULL documenté pour la tranche 6 : lookup exact avec `tenantId` explicite, pas une valeur `undefined`), sinon le modèle global (`tenantId: null`), sinon `null` (catégorie non modélisée, comportement inchangé : `input.title`/`input.body` tels quels). Quand un modèle existe : `subject` remplace `input.title`, et `bodyFr`/`bodyEn` (choisi par `UserProfile.locale` du parent, `"fr"` par défaut) remplace `input.body` — avec un seul point de substitution `{{message}}` où s'insère le texte concret déjà calculé par l'appelant (élève, sévérité...). Volontairement pas un moteur de gabarit complet à variables multiples : un modèle sans `{{message}}` reste un texte statique tel quel, une seule chose à substituer pour ce périmètre.

**Restent hors périmètre** : PUSH (aucune infrastructure de jetons d'appareil/APNs/FCM dans ce code — pas de client mobile), quotas par plan, intégration WhatsApp. `Announcement` (diffusion générale) et `SupportTicket` (tickets de support) sont désormais faits — voir les sections dédiées ci-dessous.

## Canaux de notification réels — email (SMTP) et SMS (Twilio)

Ferme le dernier volet transversal resté ouvert dans le code : jusqu'ici, tout jeton/code (vérification email/téléphone §34, code d'activation §8) n'était que renvoyé en clair dans la réponse HTTP, et `notifyParentsOfStudent` restait IN_APP seul — « aucun fournisseur EMAIL/SMS réel n'existe dans ce code » était répété à l'identique à quatre endroits. Résolu par un adaptateur générique par canal plutôt qu'un branchement ad hoc par fournisseur, même philosophie que `payment-providers/registry.ts` pour Mobile Money (§24) : « enregistrer un adaptateur réel est la seule étape nécessaire pour l'activer, rien d'autre ne change ».

- **[lib/email-provider](../apps/api/src/lib/email-provider/)** / **[lib/sms-provider](../apps/api/src/lib/sms-provider/)** : `types.ts` (interface `EmailProviderAdapter`/`SmsProviderAdapter`, un `send()` chacun), `registry.ts` (emplacement unique actif — contrairement aux providers de paiement, il n'y a jamais qu'un seul canal email et un seul canal SMS actifs pour toute l'app, pas un routage par code comme `PaymentProvider`), `smtp-adapter.ts`/`twilio-adapter.ts` (implémentations concrètes, `Transporter`/client Twilio injectables pour les tests), `send-email.ts`/`send-sms.ts` (point d'entrée unique utilisé par les appelants — _fire-and-forget_, ne fait jamais échouer la requête qui déclenche l'envoi, no-ope avec une ligne de log si aucun adaptateur n'est enregistré).
- **[lib/notification-channels.ts](../apps/api/src/lib/notification-channels.ts)** : `bootstrapNotificationChannels()`, appelée une fois au démarrage (`index.ts`) — enregistre `SmtpEmailAdapter`/`TwilioSmsAdapter` seulement si toutes les variables `SMTP_*`/`TWILIO_*` correspondantes sont renseignées. Toutes optionnelles dans `env.ts` (premier bloc de configuration non obligatoire de ce fichier) : tant qu'elles sont absentes, le comportement reste exactement celui d'avant (jeton/code renvoyé dans la réponse, rien d'autre ne se passe) — jamais un boot qui échoue faute d'identifiants SMTP/Twilio.
- **Câblage** (`sendEmail`/`sendSms` coexistent toujours avec le comportement précédent, jamais un remplacement) : `auth.service.ts` (`registerUser`, `resendEmailVerification`, `resendPhoneVerification` — email/SMS de vérification), `family/activation-invitation.service.ts` (`createInvitation` — email si `invitedEmail`, SMS si `invitedPhone`, les deux si les deux sont fournis), `communication/notification.service.ts` (`notifyParentsOfStudent` — copie email en plus de l'IN_APP, voir section dédiée ci-dessus), `platform-admin/support-ticket-admin.service.ts` (`addSupportTicketMessage` — email/SMS au créateur du ticket pour toute réponse non interne de staff, voir section « Tickets de support » ci-dessous).
- **Textes en dur dans les autres appelants** (`auth.service.ts`, `family/activation-invitation.service.ts`, `platform-admin/support-ticket-admin.service.ts`) — ce sont des jetons/codes/réponses de support, pas des catégories récurrentes gérables par modèle comme `notifyParentsOfStudent` (voir « Consommation de `MessageTemplate` » ci-dessus, désormais fait pour ce dernier).

**Restent hors périmètre** : PUSH (même raison qu'au-dessus, aucun client mobile) ; fournisseur SendGrid/SES ou agrégateur SMS africain (Orange/MTN) — la conception en adaptateurs rend l'ajout trivial le jour où un contrat existe, mais aucun n'est câblé.

## Annonces — socle minimal (§28)

Trio [announcement.validation/.service/.controller.ts](../apps/api/src/modules/communication/) ajouté au module `communication` existant. Nouvelle permission **`communication.manage`** (`prisma/seed/data/roles-permissions.ts` et `apps/api/src/test/global-setup.ts`, qui seed indépendamment pour les tests) — accordée à `SCHOOL_OWNER`, `SCHOOL_ADMIN`, `DIRECTOR` ; aucune permission de lecture staff séparée n'existe (créer implique aussi lister/supprimer pour ce périmètre).

## Tickets de support — §31 tranche 5 (création côté tenant + triage côté super-admin)

`SupportTicket`/`SupportTicketMessage` ([communication.prisma](../prisma/schema/communication.prisma)) existaient au schéma sans code applicatif, comme `PromotionCode` avant la tranche 4. Contrairement aux autres ressources §31 (pilotées uniquement par le super-admin), un ticket n'a de sens que si un membre du tenant peut en ouvrir un — module à deux versants, tous deux nécessaires pour clore §31 sur ce point :

- **Côté tenant** (`communication` module, [support-ticket.service.ts](../apps/api/src/modules/communication/support-ticket.service.ts)) : `POST/GET /communication/support-tickets`, `GET /communication/support-tickets/:id`, `POST /communication/support-tickets/:id/messages` — `requireAuth, enforceTenantScope, requireTenantMembership`, sans permission dédiée (ouvrir un ticket est un geste self-service de base). Un ticket n'est visible/modifiable que par son créateur (`createdByUserId`), pas par l'ensemble du personnel du tenant — même logique de propriété que `notification.service.ts:requireOwnNotification`. Les notes internes (`isInternalNote: true`, écrites côté super-admin) sont explicitement filtrées de la réponse tenant. Un ticket `CLOSED` refuse un nouveau message (409 `SUPPORT_TICKET_CLOSED`) des deux côtés.
- **Côté super-admin** (`platform-admin` module, [support-ticket-admin.service.ts](../apps/api/src/modules/platform-admin/support-ticket-admin.service.ts)) : `GET /platform/support-tickets` (filtrable `?tenantId=&status=&priority=&assignedToUserId=`), `GET /platform/support-tickets/:id` (historique complet, notes internes comprises), `POST /platform/support-tickets/:id/assign` (vérifie l'existence de l'utilisateur cible, 404 `USER_NOT_FOUND` sinon), `PATCH /platform/support-tickets/:id/status` (pose/efface `closedAt` selon `CLOSED` ou non), `POST /platform/support-tickets/:id/messages` (`isInternalNote` optionnel).
- **Garde de rôle spécifique à ce sous-domaine** : le seed ([roles-permissions.ts](../prisma/seed/data/roles-permissions.ts)) accorde la permission `platform.support.manage` à `SUPER_ADMIN` et au rôle dédié `SUPPORT_AGENT` (déjà présent au seed, jusqu'ici inutilisé) — **pas** à `PLATFORM_ADMIN`. Plutôt que de réutiliser `readPlatform`/`managePlatform` (communs aux autres tranches §31), ce module définit ses propres gardes `readPlatformSupport` (`SUPER_ADMIN`, `PLATFORM_ADMIN`, `PLATFORM_AUDITOR`, `SUPPORT_AGENT` — lecture) et `manageSupportTickets` (`SUPER_ADMIN`, `SUPPORT_AGENT` uniquement — gestion), pour respecter cette intention déjà encodée dans le seed sans introduire de vérification par table de permissions ailleurs dans `platform-admin` (qui reste partout ailleurs basé sur le code de rôle, pas la permission).
- Comme les tranches 3 et 4, la justification reste **optionnelle** pour assigner/répondre/changer le statut — ce n'est pas le type d'intervention (vérification, suspension, transition d'abonnement) que §31 rend explicitement obligatoire de justifier. `recordAuditLog` trace quand même chaque écriture, avec le `tenantId` du ticket cette fois (contrairement aux tranches 3/4 dont les ressources n'ont pas de tenant).
- **Notification du créateur (§28)** : `addSupportTicketMessage` envoie désormais `sendEmail`/`sendSms` (email toujours, SMS en plus si l'auteur a un `phone`) à `ticket.createdByUserId` pour toute réponse **non interne** de staff — jamais pour une `isInternalNote`, qui reste réservée à l'équipe. Même comportement no-op tant qu'aucun fournisseur SMTP/Twilio n'est configuré (`lib/notification-channels.ts`) ; le ticket reste de toute façon consultable en le rouvrant côté tenant, ce canal s'ajoute plutôt qu'il ne remplace.

**Restent hors périmètre** : SLA/escalade automatique par priorité.

## Portail parent — §25 (lecture seule, Phase 8)

Nouveau module [parent-portal](../apps/api/src/modules/parent-portal/), monté sur `/api/v1/parent-portal`. Toutes les routes : `requireAuth, requireVerifiedStudentRelationship()` (jamais `enforceTenantScope`/`requireTenantMembership` — le parent n'est membre d'aucun tenant côté enfant) ; chemins imbriqués sous `/children/:studentId/...` puisque le résolveur par défaut du middleware lit `req.params.studentId`. Composé uniquement d'appels vers les services déjà existants (`parent-portal.service.ts` n'a aucune logique métier propre) :

- `GET .../attendance` → `attendanceService.listAttendance({studentId, ...})`.
- `GET .../report-cards`, `GET .../report-cards/:id`, `GET .../report-cards/:id/pdf` → services de `grading`, avec vérification explicite `reportCard.studentId === studentId` (404, jamais 403 — ne jamais confirmer l'existence du bulletin d'un autre élève).
- `GET .../timetable` → `requireCurrentEnrollment(studentId)` pour la classe/année courantes, puis `timetableService.listTimetables`/`listTimetableEntries`.
- `GET .../announcements` → `listAnnouncementsForStudent(studentId, "PARENTS")`.
- `GET .../finance/situation` → `getStudentFinancialSituation(studentId)` (import cross-module depuis `finance`, même convention que `finance` impute déjà `students/student.service.ts`).
- `GET .../receipts/:receiptId/pdf` → vérifie que la facture du paiement du reçu appartient à `studentId` (404 sinon), réutilise `generateReceiptPdf` tel quel.

**Deux changements partagés nécessaires pour rendre tout ça réutilisable sans dupliquer de logique** :

- `requireVerifiedStudentRelationship` ([middleware](../apps/api/src/middleware/requireVerifiedStudentRelationship.ts)) peuple désormais aussi `req.tenant` (même forme qu'`enforceTenantScope`) après avoir trouvé la relation vérifiée — les handlers PDF existants (bulletin, reçu) lisent `req.tenant.name` et étaient jusque-là inutilisables hors d'une route `enforceTenantScope`.
- `requireCurrentEnrollment(studentId)` existait en privé dans `id-card.service.ts` (§19) ; déplacé et exporté depuis `students/student.service.ts`, réutilisé par le timetable, les annonces, et toujours par la carte scolaire.

**Restent hors périmètre** : rien de spécifique au portail parent lui-même. La gestion par le parent de son propre abonnement SaaS/factures (§9, abonnement familial en libre-service) est désormais faite — voir la section dédiée plus haut, exposée en lecture par `GET .../dashboard` (`subscription`, section §18 ci-dessous). Les préférences de notification (`GET/PUT .../notification-preferences`, canal EMAIL uniquement) sont désormais faites — voir « Notifications aux parents » plus haut. Le portail élève (§26) est désormais fait — voir la section dédiée ci-dessous.

## Portail élève — §26 (lecture seule, Phase 8)

Chemin d'accès différent du portail parent : un `Student` devient consultable par un `User` via `StudentUserLink` (créé exclusivement par la rédemption d'un code d'activation catégorie `STUDENT`, §8 — jamais par simple authentification), pas via `ParentStudentRelationship`.

- **Problème bloquant résolu avant de construire le portail** : `requireVerifiedStudentRelationship` peut peupler `req.tenant` uniquement parce que `ParentStudentRelationship` porte déjà `tenantId` (ajouté précisément pour ce bootstrap). `StudentUserLink` n'avait **aucune colonne `tenantId`** — la seule façon de le retrouver aurait été de lire `Student.tenantId` via `rawPrisma`, bloqué par la RLS de `Student` (même bug que celui corrigé pour `ActivationInvitation`). Migration `20260813090037_student_user_link_tenant_id` : ajoute `tenantId` (backfillé depuis `Student.tenantId`), **sans jamais activer RLS** dessus (même raisonnement que `TenantDomain`/`ParentStudentRelationship`/`ActivationInvitation`), ajouté à `TENANT_SCOPED_MODELS` pour le garde applicatif. `redeemActivation` (famille, §8) pose maintenant `tenantId` à la création du lien.
- **`requireLinkedStudent`** ([middleware](../apps/api/src/middleware/requireLinkedStudent.ts)) : même structure que `requireVerifiedStudentRelationship` — résout `studentId`, vérifie `StudentUserLink.userId === req.user.id` (403 `STUDENT_LINK_NOT_VERIFIED` sinon — pas de statut `VERIFIED` distinct : l'existence du lien EST la vérification), peuple `req.tenant`, verrouille le contexte tenant.
- **`GET /family/linked-students`** ([student-user-link.service.ts](../apps/api/src/modules/family/student-user-link.service.ts)) : symétrique à `GET /family/children`, devenu trivial maintenant que `StudentUserLink` porte `tenantId` — chaque `Student` lu via `withTenantSession(link.tenantId, …)`, pas de dérogation RLS supplémentaire sur `Student` lui-même (donnée sensible).
- Nouveau module [student-portal](../apps/api/src/modules/student-portal/), monté sur `/api/v1/student-portal`, chemins imbriqués sous `/students/:studentId/...`, toutes les routes `requireAuth, requireLinkedStudent()` : `GET .../profile` (`getStudent` + `requireCurrentEnrollment`, tolérant — `null` si pas d'inscription active), `GET .../timetable` (même composition que le portail parent), `GET .../report-cards`/`:id`/`:id/pdf` (mêmes services `grading`, même garde d'appartenance 404), `GET .../announcements` (`listAnnouncementsForStudent(studentId, "STUDENTS")`), `GET .../receipts` (nouveau `listReceiptsForStudent`, `finance/student-payment.service.ts`) et `GET .../receipts/:receiptId/pdf` (même garde d'appartenance que le portail parent).
- **Abonnement SaaS individuel de l'élève** (`/api/v1/subscriptions/student/:studentId/...`, dans [subscription.routes.ts](../apps/api/src/modules/subscriptions/subscription.routes.ts)) : même pipeline générique que `/school` et `/family` (`createDraftSubscription` → `createInvoiceForSubscription` → `createPaymentIntent` → `recordManualCashPayment`), résolu par `studentId` via `requireLinkedStudent()` plutôt que `requireFamilyAccountForUser` — un `User` peut être lié à plusieurs `Student` au fil des transferts (§10), d'où le paramètre explicite dans l'URL plutôt qu'une résolution implicite "mon unique compte" comme pour `/family`. Aucun modèle intermédiaire type `FamilyAccount` n'était nécessaire : `SubscriptionOwner.studentId` ancre directement un abonnement `STUDENT_BASIC`/`STUDENT_PREMIUM` à siège unique, sans notion de `childrenCovered`. Le service `subscription.service.ts` n'a nécessité aucun changement (déjà générique sur `ownerType`/`ownerRef`) ; seuls le contrôleur, les routes et un `PlanPrice` de test pour `STUDENT_BASIC` manquaient. Même limite héritée que `/family` et `/school` : aucune route ne pilote `DRAFT → PENDING_PAYMENT` (seul un paiement réussi y pousse), paiement espèces uniquement.

**Restent hors périmètre** : calendrier dédié (aucun modèle d'événements/jours fériés, déjà noté hors périmètre en §20) ; paiement électronique réel pour l'abonnement de l'élève (même limite que partout ailleurs dans ce code, §24). Devoirs et dépôt de travaux (§18/§21/§25/§26) est désormais fait — voir la section dédiée ci-dessous.

## Devoirs et dépôt de travaux (§18/§21/§25/§26)

Cité dans quatre sections du cahier des charges (tableau de bord, notes et évaluations, portails parent/élève) sans jamais y posséder son propre module — et explicitement laissé en jachère : « aucun modèle `Homework` au schéma, décision de schéma non prise ». Décision prise ici : un `Homework`/`HomeworkSubmission` (`homework.prisma`) **distinct** d'`Assessment`/`Grade` — l'énoncé, l'échéance et le dépôt de travail, jamais une note chiffrée (ça reste le rôle de §21 si un établissement veut noter un devoir, via un `AssessmentType` dédié).

- **`Homework`** : `classroomId`/`subjectId` (le premier reste un champ nu, sans relation Prisma, même choix que `Attendance.classroomId`/`Assessment.classroomId` ailleurs dans ce schéma), `title`/`instructions`/`dueAt`, `createdByEmployeeId` résolu côté serveur (`resolveActingEmployeeId`, jamais un id fourni par le client — même garde que `discipline`/`attendance`), suppression douce (`deletedAt`).
- **`HomeworkSubmission`** : `content`/`fileUrl` (au moins l'un des deux, validé côté Zod) — `fileUrl` suit exactement le précédent `StudentDocument` (§19) : une URL déjà uploadée par le client ailleurs, cette API ne manipule jamais les octets du fichier. Contrainte unique `(homeworkId, studentId)` : un redépôt met à jour la soumission existante via `upsert`, jamais un doublon (même raisonnement que l'appel de présence idempotent, §22). Le statut `ON_TIME`/`LATE` est calculé côté serveur à l'instant du dépôt (`submittedAt > homework.dueAt`), jamais fourni par le client.
- Nouveau module [homework](../apps/api/src/modules/homework/), monté sur `/api/v1/homework`, derrière `homework.read`/`homework.write` côté enseignant/staff tenant (`POST/GET /homework`, `GET/PATCH/DELETE /homework/:id`, `GET /homework/:id/submissions` pour que l'enseignant voie qui a soumis) — même structure CRUD + suppression douce que `discipline`.
- **Dépôt par l'élève** (`/homework/student/:studentId/...`) : même raisonnement que l'abonnement individuel de l'élève (§26 ci-dessus) — jamais `enforceTenantScope`/`requireTenantMembership`, résolu par `studentId` via `requireLinkedStudent()`. `GET .../student/:studentId` liste les devoirs de la classe **courante** de l'élève (`requireCurrentEnrollment`, jamais un `classroomId` fourni par le client — même principe que le timetable/les annonces du portail élève) ; `POST .../:homeworkId/submit` et `GET .../:homeworkId/submission` vérifient qu'un devoir demandé appartient bien à cette classe (404, jamais 403 — ne jamais confirmer l'existence d'un devoir d'une autre classe).
- **`GET /parent-portal/children/:studentId/homework`** (§25 : « consulter les devoirs ») : même liste en lecture seule, réutilise `listHomeworkForStudent` tel quel — le dépôt du travail reste une action de l'élève, jamais du parent.
- **Tableaux de bord (§18)** : `GET /dashboard/enseignant` expose désormais `upcomingHomework` (mêmes `assignedClassroomIds`/`assignedSubjectIds` que `upcomingAssessments`) ; `GET /student-portal/students/:studentId/dashboard` expose `upcomingHomework` (devoirs de la classe courante non encore échus).

**Reste hors périmètre** : notation d'un devoir (couvert par §21 via `AssessmentType` si un établissement le souhaite, pas dupliqué ici), historique des devoirs par matière au-delà de la liste simple, pièce jointe multiple par soumission (un seul `fileUrl`).

## E-learning — §29 (Phase 10)

« Apprentissage en ligne » n'était qu'une ligne dans la liste des modules complémentaires (§29), sans détail fonctionnel — même situation que §27 (RH) et la bibliothèque avant leurs tranches respectives. Décision de schéma prise ici, sur le modèle exact de `Homework`/`HomeworkSubmission` (même granularité classe/matière, mêmes conventions) : un `OnlineCourse` composé de `CourseResource` (ressources pédagogiques), avec suivi de progression par `ResourceProgress`.

- **`OnlineCourse`** (`classroomId`/`subjectId`, champ nu comme `Homework.classroomId`) : `title`/`description`, `createdByEmployeeId` résolu côté serveur, suppression douce.
- **`CourseResource`** : `type` (`VIDEO`/`DOCUMENT`/`LINK`/`TEXT`), `url`/`content` (au moins l'un des deux, validé côté Zod — `url` suit le même choix que `StudentDocument`/`HomeworkSubmission.fileUrl` : un lien déjà hébergé ailleurs, cette API ne manipule jamais d'octets de fichier ni n'héberge de vidéo), `order` pour l'affichage séquentiel.
- **`ResourceProgress`** : contrainte unique `(resourceId, studentId)` — marquer une ressource terminée est un `upsert`, jamais un historique de consultations à rallonge (même raisonnement que le redépôt de devoir).
- Nouveau module [elearning](../apps/api/src/modules/elearning/), monté sur `/api/v1/elearning`, derrière `elearning.read`/`elearning.write` (mêmes rôles que `homework.read`/`write`) : `POST/GET /courses`, `GET/PATCH/DELETE /courses/:id`, `POST/GET/DELETE /courses/:id/resources[/:resourceId]`, `GET /courses/:id/progress` (liste les `ResourceProgress` réels du cours — jamais une ligne fabriquée à zéro pour un élève qui n'a encore rien terminé, même choix que `listSubmissionsForHomework`).
- **Consultation par l'élève** (`/elearning/student/:studentId/...`) : même raisonnement que le dépôt de devoir — jamais `enforceTenantScope`/`requireTenantMembership`, résolu par `requireLinkedStudent()`. `GET .../courses` liste les cours de la classe **courante** de l'élève (`requireCurrentEnrollment`, jamais un `classroomId` client-fourni) ; `GET .../courses/:courseId` vérifie l'appartenance à cette classe (404, jamais 403) et renvoie les ressources plus `completedResourceIds` en un seul appel ; `POST .../resources/:resourceId/complete` marque la progression (idempotent).

**Restent hors périmètre** : intégration aux tableaux de bord/portails existants (§18/§25/§26 — ce module reste autonome, à l'inverse des devoirs qui y sont exposés), quiz/évaluation en ligne (couvert par §21 si besoin, pas dupliqué ici), hébergement vidéo natif (URL externe uniquement, même limite que partout ailleurs dans ce code pour les fichiers).

## Transport scolaire — §29 (Phase 10)

Même absence de détail fonctionnel que §29 pour la bibliothèque/le RH/l'e-learning avant leurs tranches. Le rôle `TRANSPORT_MANAGER` existait déjà au seed sans aucune permission à piloter (`ROLE_PERMISSIONS.TRANSPORT_MANAGER: []`) — cette tranche lui en donne enfin. Décision de schéma : véhicules → itinéraires (avec arrêts ordonnés) → affectation d'un élève à un itinéraire/arrêt → suivi quotidien du trajet.

- **`Vehicle`** : `plateNumber` unique par tenant, `capacity`, `status` (`ACTIVE`/`MAINTENANCE`/`RETIRED`) — même paire suppression douce + statut terminal que `Book`/`Employee` (`retireVehicle` pose `deletedAt` et `status: RETIRED` ensemble).
- **`TransportRoute`** : `vehicleId` (FK réelle vers `Vehicle`, optionnelle — un itinéraire peut exister avant qu'un véhicule lui soit affecté) et `driverEmployeeId` (champ nu, comme `Homework.createdByEmployeeId`/`LibraryLoan.issuedByEmployeeId` ailleurs dans ce schéma — vérifié côté service, jamais une relation Prisma pour ce FK précis).
- **`RouteStop`** : arrêts ordonnés (`order`) par itinéraire, `time` en `"HH:MM"` (même convention que `TimetableEntry.startTime`, une heure indicative).
- **`StudentRouteAssignment`** : `@@unique([studentId])` — un seul itinéraire actif par élève, réaffecter (`upsert`) remplace l'affectation existante plutôt que d'empiler un historique.
- **`TransportAttendance`** (suivi des trajets) : `@@unique([routeId, studentId, date])`, upsert natif par jour — contrairement à `Attendance` (élèves en classe), aucune colonne nullable dans cette contrainte, donc pas le piège NULL documenté sur `recordRollCall`, même raisonnement que `EmployeeAttendance`.
- Nouveau module [transport](../apps/api/src/modules/transport/), monté sur `/api/v1/transport`, derrière `transport.read`/`transport.write` (`SCHOOL_OWNER` + `TRANSPORT_MANAGER` en écriture, `SCHOOL_ADMIN`/`TENANT_AUDITOR` en lecture seule) : CRUD véhicules (avec retrait), CRUD itinéraires + arrêts, affectation/réaffectation/désaffectation d'élève, enregistrement/consultation du suivi quotidien.

**Restent hors périmètre** : portail parent/élève (aucune consultation self-service de l'itinéraire/l'horaire, à l'inverse des devoirs et de l'e-learning), géolocalisation temps réel du véhicule, facturation d'un supplément transport (aucun lien avec `StudentInvoice`/`FeeStructure`).

## Cantine — §29 (Phase 10)

Dernier module avant l'internat, même absence de détail fonctionnel que §29 pour les tranches précédentes. Nouveau rôle `CAFETERIA_MANAGER` (même précédent que `LIBRARIAN`/`TRANSPORT_MANAGER` pour leurs modules). Décision de schéma : menus (information affichée) → formules de repas → inscription d'un élève à une formule → suivi des paiements (statut simple) → suivi quotidien des repas pris.

- **`Menu`** : une ligne par jour (`@@unique([tenantId, date])`), information affichée à tous — jamais liée à une inscription particulière, le menu du jour est le même pour tout le monde.
- **`MealPlan`** : `priceCents` (entier, §23/§40 — jamais de calcul flottant), `type` (`DAILY`/`WEEKLY`/`MONTHLY`), même paire suppression douce que `Book`/`Vehicle` (`archiveMealPlan`).
- **`StudentMealEnrollment`** : **pas** de contrainte unique sur `studentId` seul (contrairement à `StudentRouteAssignment`) — un élève accumule légitimement plusieurs inscriptions dans le temps (formules successives). La règle « une seule inscription `ACTIVE` à la fois » est vérifiée côté service par requête, pas par un index — même choix que « un prêt actif par élève et par livre » en bibliothèque (contrainte métier, pas un contraintes de schéma). `paid`/`paidAt` : un statut de paiement simple, **aucun lien avec `StudentInvoice`/`FeeStructure`** — pas une vraie facture, décision assumée pour cette tranche (voir note de schéma).
- **`MealAttendance`** (suivi des repas) : `@@unique([enrollmentId, date])`, upsert natif par jour — même forme que `TransportAttendance`/`EmployeeAttendance`.
- Nouveau module [cafeteria](../apps/api/src/modules/cafeteria/), monté sur `/api/v1/cafeteria`, derrière `cafeteria.read`/`cafeteria.write` (`SCHOOL_OWNER` + `CAFETERIA_MANAGER` en écriture, `SCHOOL_ADMIN`/`TENANT_AUDITOR` en lecture seule) : CRUD menus, CRUD formules (avec archivage), inscription/paiement/annulation, enregistrement/consultation du suivi quotidien.

**Restent hors périmètre** : portail parent/élève (même choix que le transport), facturation réelle via `StudentInvoice`/`FeeStructure` (voir note ci-dessus), gestion des allergies/régimes alimentaires.

## Internat — §29 (dernier module de la Phase 10)

Dernier module complémentaire listé par §29. Nouveau rôle `BOARDING_MANAGER` (même précédent que `LIBRARIAN`/`TRANSPORT_MANAGER`/`CAFETERIA_MANAGER`). Décision de schéma : chambres → lits → affectation d'un élève à un lit → suivi des présences nocturnes.

- **`DormitoryRoom`** : `name` unique par tenant, `capacity`, même paire suppression douce que `Book`/`Vehicle`/`MealPlan` (`archiveRoom`).
- **`DormitoryBed`** : pas de statut `ACTIVE`/`OUT_OF_SERVICE` séparé — un lit hors service se retire directement (`DELETE`), bloqué (409 `BED_OCCUPIED`) tant qu'un élève y est affecté. Contrairement aux autres modules complémentaires, la FK `StudentBedAssignment.bedId` est en `RESTRICT` (pas `CASCADE`) précisément pour ça — vérifié aussi côté service pour renvoyer une erreur propre plutôt que de laisser remonter la contrainte Postgres brute.
- **`StudentBedAssignment`** : **`studentId` ET `bedId` uniques tous les deux** (contrairement à `StudentRouteAssignment`, qui n'a que `studentId`) — un lit n'a qu'un seul occupant à la fois, la contrainte l'impose directement en base plutôt qu'un contrôle côté service seul. Réaffecter un élève vers un autre lit (`upsert` par `studentId`) libère donc automatiquement son ancien lit ; assigner un lit déjà occupé par un _autre_ élève est explicitement refusé (409 `BED_OCCUPIED`) avant d'atteindre la contrainte.
- **`DormitoryAttendance`** (présences nocturnes) : `@@unique([assignmentId, date])`, upsert natif par nuit — même forme que `TransportAttendance`/`MealAttendance`.
- Nouveau module [boarding](../apps/api/src/modules/boarding/), monté sur `/api/v1/boarding`, derrière `boarding.read`/`boarding.write` (`SCHOOL_OWNER` + `BOARDING_MANAGER` en écriture, `SCHOOL_ADMIN`/`TENANT_AUDITOR` en lecture seule) : CRUD chambres (avec archivage) + lits (occupation visible directement dans la liste des lits, `include: { assignment }`), affectation/réaffectation/désaffectation d'élève, enregistrement/consultation du suivi nocturne. Cette dernière tranche clôt la Phase 10 (modules complémentaires) dans son intégralité.

**Restent hors périmètre** : portail parent/élève (même choix que le transport et la cantine), facturation d'un supplément internat (même limite assumée que le transport/la cantine).

## Tableaux de bord — §18

Aucun code n'existait pour §18 avant cette tranche, hormis le super-admin (`stats-admin.service.ts`, §31 tranche 9, couvre déjà tout ce que §18 liste pour ce rôle qui a une source de données réelle). Les cinq autres rôles (Direction, Comptable, Enseignant, Parent, Élève) sont des **agrégations en lecture seule** au-dessus de services déjà existants — aucune nouvelle donnée métier, uniquement de l'orchestration, même discipline que `stats-admin.service.ts` (agrégé en mémoire/`groupBy`, jamais un total qui suppose une donnée absente du schéma).

Nouveau module [dashboard](../apps/api/src/modules/dashboard/), monté sur `/api/v1/dashboard`, `requireAuth, enforceTenantScope, requireTenantMembership` :

- **`GET /dashboard/direction`** ([direction-dashboard.service.ts](../apps/api/src/modules/dashboard/direction-dashboard.service.ts)) : élèves (total, répartition par statut/sexe/classe, inscriptions récentes), personnel (répartition par statut), taux de présence (`Attendance.groupBy` sur une fenêtre glissante, `windowDays` par défaut 30 — même défaut que §31 tranche 9), moyenne des bulletins (toutes périodes confondues — §21 n'a pas de notion de "période courante" indépendante de chaque bulletin), finances (facturé/encaissé/impayés cumulés + recettes/dépenses de la fenêtre, en réutilisant `financial-report.service.ts` §23 tranche 5 plutôt que de dupliquer l'agrégation), incidents disciplinaires récents. Gardé par `finance.read` **et** `discipline.read` ensemble plutôt que l'un ou l'autre seul : `finance.read` seul laisserait un `ACCOUNTANT` y accéder (il a déjà son propre tableau de bord ci-dessous) ; `discipline.read` en plus (absent du rôle `ACCOUNTANT`) restreint exactement à `SCHOOL_OWNER`/`SCHOOL_ADMIN`/`DIRECTOR`/`TENANT_AUDITOR`.
- **`GET /dashboard/comptable`** ([accountant-dashboard.service.ts](../apps/api/src/modules/dashboard/accountant-dashboard.service.ts)) : encaissements du jour et paiements récents, factures par statut + impayés/échéances à venir (fenêtre 7 jours), recettes/dépenses de la période, caisse (session ouverte + dernières clôtures). Gardé par `finance.read` seul (`SCHOOL_OWNER`, `SCHOOL_ADMIN`, `DIRECTOR`, `ACCOUNTANT`, `TENANT_AUDITOR`).
- **`GET /dashboard/enseignant`** ([teacher-dashboard.service.ts](../apps/api/src/modules/dashboard/teacher-dashboard.service.ts)) : entièrement **auto-scopé par l'`Employee` lié à l'appelant** (`EMPLOYEE_RECORD_REQUIRED` sinon, même garde que `finance`/`attendance`/`discipline`), jamais par un paramètre — classes affectées, cours du jour (`TimetableEntry.dayOfWeek`, conversion JS `getDay()` ↔ schéma "0 = lundi"), classes où l'appel n'a pas encore été fait aujourd'hui, évaluations à venir non publiées, devoirs à venir (`upcomingHomework`, mêmes `assignedClassroomIds`/`assignedSubjectIds`, voir §18/§21/§25/§26 ci-dessus), annonces `ALL`/`STAFF`/`TEACHERS`. Gardé par `attendance.read` (le plus largement détenu par les rôles encadrants/enseignants) — le contenu reste vide pour quiconque n'a pas de classe affectée, sans risque de fuite puisque tout est filtré par `employeeId`. **"Notes manquantes" (§18) volontairement absent** : un diff fiable élève-par-élève/évaluation-par-évaluation n'existe nulle part ailleurs dans ce code, l'approximer risquerait d'afficher un chiffre trompeur.

**Parent et Élève** restent dans leurs modules existants plutôt qu'un `dashboard` générique, puisqu'ils sont déjà scopés par relation/lien plutôt que par tenant :

- **`GET /parent-portal/dashboard`** (pas de `:studentId` — agrège tous les enfants vérifiés du parent) : chaque enfant tourne sous `runWithContext` verrouillé sur **son propre** tenant (§9 : un parent peut avoir des enfants dans des établissements différents), exactement comme `requireVerifiedStudentRelationship` le fait pour les routes à un seul enfant — jamais un contexte tenant partagé pour toute la liste. Présences récentes, dernier bulletin (le plus récent par `generatedAt`, pas par `classRank` — l'ordre par défaut de `listReportCards`), situation financière, annonces, par enfant, plus `subscription` au niveau du foyer (`null` si le parent n'a pas encore de `FamilyAccount`, jamais un abonnement fabriqué — géré de bout en bout depuis `/api/v1/subscriptions/family`, §9 ci-dessus).
- **`GET /student-portal/students/:studentId/dashboard`** : bundle des mêmes endpoints déjà exposés individuellement par ce module (profil, cours du jour, bulletins récents, annonces), plus `upcomingHomework` (devoirs de la classe courante non encore échus, voir §18/§21/§25/§26 ci-dessus) et l'abonnement de l'élève lui-même (`findSubscriptionForOwner({studentId})`), gérable de bout en bout depuis `/api/v1/subscriptions/student/:studentId/...` (voir section §26 ci-dessus). "Calendrier" reste hors périmètre, mêmes raisons que documentées plus haut pour le portail élève.

## Super-administration — établissements, journaux d'audit, abonnements (§31, Phase 9 démarrée)

§31 veut une interface séparée gérant ~23 catégories de données plateforme (établissements, abonnements, licences, paiements, codes promo, support, pays/devises, statistiques, journaux d'audit...), avec une règle transversale explicite : toute intervention d'un administrateur global dans un tenant doit être autorisée, **justifiée**, limitée dans le temps, **visible dans les audits**, et respecter le moindre privilège. Avant cette tranche, la plomberie existait mais n'était câblée nulle part : `requirePlatformRole` ([middleware](../apps/api/src/middleware/requirePlatformRole.ts)) et `userHasPlatformRole` (`UserRole.tenantId = null` = portée plateforme) étaient écrits et fonctionnels mais zéro route ne les utilisait ; `AuditLog` (schéma Phase 2, champ `justification` déjà commenté « obligatoire pour toute intervention globale dans un tenant (§31) ») n'avait aucun écrivain.

Cette tranche construit la fondation que la règle transversale exige, appliquée à un premier domaine cohérent — **établissements** — plutôt que de saupoudrer un peu de chaque catégorie de §31. Nouveau module [platform-admin](../apps/api/src/modules/platform-admin/), monté sur `/api/v1/platform`, **jamais** `enforceTenantScope`/`requireTenantMembership` (action cross-tenant par nature — le `rawPrisma` du projet documente déjà ce cas d'usage explicitement) :

- **`recordAuditLog`** ([lib/audit-log.ts](../apps/api/src/lib/audit-log.ts)) : premier écrivain d'`AuditLog`, réutilisable par toute future action super-admin. Écrit sur `rawPrisma` (journal cross-tenant, hors garde tenant par nature — `tenantId` nullable).
- **Établissements** (`tenant-admin.service.ts`) : `GET /platform/tenants` (filtrable `?status=&search=`), `GET /platform/tenants/:id`, `POST /platform/tenants/:id/verify|reject|suspend|reactivate`. Chaque action mutante exige `{justification}` (400 sinon), vérifie la transition de statut autorisée (`PENDING_VERIFICATION → VERIFIED|REJECTED`, `{VERIFIED,TRIAL,ACTIVE} → SUSPENDED`, `SUSPENDED → ACTIVE` — 409 sinon), et journalise systématiquement (`beforeData`/`afterData` = `{status}` seulement, jamais la ligne complète — proportionné).
- **Moindre privilège** : lecture (`GET /platform/tenants*`, `GET /platform/audit-logs`) ouverte à `SUPER_ADMIN`, `PLATFORM_ADMIN` **et `PLATFORM_AUDITOR`** (comble au passage le rôle auditeur, jusqu'ici sans aucune permission) ; mutation (`POST /platform/tenants/:id/...`) restreinte à `SUPER_ADMIN`/`PLATFORM_ADMIN`.
- **`actorRoleCode`** résolu via `getPlatformRoleCodes` (nouvel export de `lib/authorization.ts`, extraction de la fonction déjà privée qui liste les rôles plateforme actifs d'un utilisateur) — premier rôle actif trouvé, journalisé à chaque action. `resolveActor`/`PlatformActor` extraits dans [platform-actor.ts](../apps/api/src/modules/platform-admin/platform-actor.ts), partagés entre tous les sous-modules `platform-admin` (pas dupliqués par domaine).

**Correctif (audit de couverture complet §1-§41) — suspendre un établissement était cosmétique** : `POST /platform/tenants/:id/suspend` écrivait bien `status: "SUSPENDED"` et l'entrée d'audit, mais rien en aval ne consultait jamais ce statut — `enforceTenantScope` ([middleware/enforceTenantScope.ts](../apps/api/src/middleware/enforceTenantScope.ts)) ne bloquait que `REJECTED`/`CANCELLED`. Le personnel d'un établissement suspendu (fraude, impayé, litige) continuait donc de se connecter et d'opérer normalement sur toutes ses données. Même liste tronquée dupliquée dans `resolveDestinationTenant` ([students/transfer.service.ts](../apps/api/src/modules/students/transfer.service.ts)) — un transfert pouvait viser un établissement suspendu comme destination. Fermé en extrayant la liste dans un point unique, [lib/tenant-status.ts](../apps/api/src/lib/tenant-status.ts) (`isTenantBlocked`, désormais `REJECTED`/`CANCELLED`/`SUSPENDED`), consommé par les deux — pour ne pas laisser cette liste diverger une deuxième fois silencieusement. Testé dans [platform-admin.test.ts](../apps/api/src/test/integration/platform-admin.test.ts) : un membre ordinaire du tenant suspendu est bloqué (403 `TENANT_UNAVAILABLE`) sur une route tenant ordinaire pendant la suspension, et retrouve l'accès dès la réactivation.

**Abonnements — tranche 2** (`subscription-admin.service.ts`) : `GET /platform/subscriptions` (filtrable `?status=&ownerType=`), `GET /platform/subscriptions/:id` (avec l'historique `SubscriptionEvent`), `POST /platform/subscriptions/:id/transition` et `POST /platform/subscriptions/:id/extend-trial`, même garde moindre-privilège (lecture `PLATFORM_AUDITOR` inclus, mutation restreinte). Réutilise `transitionSubscription`/`applySubscriptionTransition` ([subscriptions/subscription.service.ts](../apps/api/src/modules/subscriptions/subscription.service.ts)) tels quels — déjà génériques (`subscriptionId` brut, aucun scoping tenant, table `ALLOWED_SUBSCRIPTION_TRANSITIONS` déjà validée : `PAST_DUE→GRACE_PERIOD`, `SUSPENDED→ACTIVE` etc. déjà autorisés, `CANCELLED`/`REFUNDED` terminaux) — un seul endpoint de transition générique couvre donc suspensions/réactivations/mise en grâce plutôt que des endpoints étroits par cas. `recordAuditLog` et le `SubscriptionEvent` déjà écrit par `applySubscriptionTransition` sont deux pistes complémentaires, pas redondantes : l'un est l'historique du cycle de vie de l'abonnement, l'autre la piste d'intervention administrative (§31). La prolongation d'essai (`extend-trial`) est la seule logique réellement nouvelle — `Subscription.trialEndsAt` existe au schéma mais n'était piloté nulle part ; exige `status === TRIAL` (409 `SUBSCRIPTION_NOT_IN_TRIAL` sinon).

**Pays, devises, moyens de paiement — tranche 3** (`reference-data-admin.service.ts`) : `GET/POST /platform/countries`, `PATCH /platform/countries/:id`, et l'équivalent pour `/currencies` et `/payment-providers`. Aucun des trois modèles n'est tenant-scoped (pas de colonne `tenantId`), donc le client gardé `prisma` suffit — pas de bootstrap `rawPrisma` nécessaire comme pour les tenants/abonnements. Doublon de code refusé (409 `COUNTRY_ISO_CODE_TAKEN`/`CURRENCY_ISO_CODE_TAKEN`/`PAYMENT_PROVIDER_CODE_TAKEN`), référence croisée vérifiée (`Country.defaultCurrencyId` → 404 `CURRENCY_NOT_FOUND` si invalide). **Différence assumée avec les tranches précédentes** : créer/modifier une devise n'est pas une « intervention dans un tenant » au sens littéral de §31 — la `justification` reste donc **optionnelle** ici (contrairement à `justifiedActionSchema` des établissements/abonnements), tout en gardant `recordAuditLog` pour la traçabilité de chaque écriture.

**Codes promotionnels — tranche 4** (`promotion-code-admin.service.ts`) : `GET/POST /platform/promotion-codes`, `PATCH /platform/promotion-codes/:id`. `PromotionCode` existait au schéma depuis la Phase 3 sans aucun code applicatif (ni service, ni contrôleur, ni seed) ; `PromotionRedemption` (la consommation d'un code lors d'une souscription) reste hors périmètre — aucun flux self-service n'applique aujourd'hui de code promo, il n'y a donc rien à brancher. Doublon de code refusé (409 `PROMOTION_CODE_TAKEN`) ; validation croisée type/valeur de remise (`discountValue` ≤ 100 si `discountType === "PERCENTAGE"`) et bornes de dates (`endsAt` après `startsAt`) faites côté zod avec `.refine()`. Même choix que la tranche 3 : créer/désactiver un code promo n'est pas une « intervention dans un tenant », la `justification` reste **optionnelle**. Le champ `Decimal(10,2)` `discountValue` est validé en `z.coerce.number()` — Prisma accepte un `number` simple en écriture, pas de conversion `Prisma.Decimal` nécessaire (même pattern que `SubjectCoefficient.coefficient`).

**Tickets de support — tranche 5** : voir la section dédiée « Tickets de support — §31 tranche 5 » plus haut (module à deux versants, `communication` côté tenant + `platform-admin` côté super-admin — sortait du périmètre des tranches purement plateforme précédentes).

**Modèles de notification — tranche 6** (`message-template-admin.service.ts`) : `GET/POST /platform/message-templates`, `PATCH/DELETE /platform/message-templates/:id`. `MessageTemplate` existait au schéma sans code applicatif, comme `PromotionCode` avant la tranche 4. `tenantId` nullable (défaut plateforme si absent, surcharge tenant si présent) mais un seul versant ici (contrairement à la tranche 5) : gérer les modèles de notification, même une surcharge tenant, reste une tâche purement d'admin plateforme. **Piège Postgres géré explicitement** : `@@unique([tenantId, code])` ne bloque pas deux lignes `tenantId: NULL` avec le même `code` (Postgres traite deux `NULL` comme non égaux dans un index unique) — le service vérifie donc l'unicité lui-même via un `findFirst` avant `create`, y compris (surtout) pour les modèles globaux, plutôt que de compter sur la contrainte SQL. Ce modèle n'a ni `isActive` ni `deletedAt` (contrairement aux ressources des tranches 3/4) : `DELETE` fait une suppression dure, seul geste qui a du sens ici. Même choix que les tranches 3-5 : la `justification` reste **optionnelle**.

**Organisations sponsors et licences sponsorisées — tranche 7** (`organization-admin.service.ts`, `license-admin.service.ts`) : `GET/POST /platform/organizations`, `PATCH/DELETE /platform/organizations/:id` (suppression douce) ; `GET/POST /platform/license-batches`, `GET /platform/license-batches/:id` (avec les licences émises) ; `GET /platform/licenses` (filtrable `?batchId=&status=&sponsorTenantId=&sponsorOrganizationId=`), `GET /platform/licenses/:id` (avec l'historique `LicenseAssignment`), `POST /platform/licenses/:id/assign`, `POST /platform/licenses/:id/revoke`. `Organization` (ONG/entreprise sponsor, distincte d'un `Tenant`) existait au schéma sans code applicatif, comme `PromotionCode` avant la tranche 4. Acheter un lot (`LicenseBatch`) émet en une transaction `quantity` `SponsoredLicense` individuelles au statut `AVAILABLE`, `fundingSource` dérivé de `purchaserType` (`TENANT` → `SCHOOL_SPONSORED`, `ORGANIZATION` → `ORGANIZATION_SPONSORED`) ; l'affectation (409 `LICENSE_NOT_AVAILABLE` si déjà assignée) crée un `LicenseAssignment` et bascule la licence à `ASSIGNED` ; la révocation (409 `LICENSE_ALREADY_REVOKED` si déjà révoquée) referme l'affectation active (`revokedAt`/`revokedReason`) et rebascule la licence à `REVOKED`. Ce module ne touche jamais un `Subscription` existant : `LicenseAssignment` trace seulement quelle licence sponsorisée couvre quel abonnement déjà créé par les flux existants (`subscriptions/subscription.service.ts`), pas de logique de facturation dupliquée. Ni `Organization` ni `LicenseBatch`/`SponsoredLicense`/`LicenseAssignment` ne sont des modèles tenant-scoped (`sponsorTenantId` est une chaîne libre indexée sur `Tenant`, pas une colonne de garde) — le client gardé `prisma` suffit, pas de bootstrap `rawPrisma`. Même choix que les tranches 3-6 : la `justification` reste optionnelle.

**Consommation des codes promotionnels — tranche 8** (`subscriptions/subscription.service.ts`) : `createDraftSubscription` accepte désormais un `promoCode` optionnel — branché sur `POST /tenants/onboarding` (souscription initiale du signup établissement, voir §14 plus bas) et `POST /subscriptions` (re-souscription ultérieure sur le portail établissement). La rédemption est validée **dans la même transaction** que la création de l'abonnement : un code invalide annule la souscription elle-même plutôt que de laisser un `DRAFT` orphelin sans code appliqué. `redeemPromotionCode` vérifie dans l'ordre : existence (404 `PROMOTION_CODE_NOT_FOUND`), `isActive` (409 `PROMOTION_CODE_INACTIVE`), fenêtre `startsAt`/`endsAt` (409 `PROMOTION_CODE_NOT_STARTED`/`PROMOTION_CODE_EXPIRED`), `applicableCategory` compatible avec le `SubscriberCategory` de l'abonnement (422 `PROMOTION_CODE_CATEGORY_MISMATCH`), puis `maxRedemptions` (409 `PROMOTION_CODE_EXHAUSTED`) ; si tout passe, crée le `PromotionRedemption` et incrémente `PromotionCode.redemptionCount` via `{ increment: 1 }` (jamais lecture-puis-écriture, qui perdrait des rédemptions concurrentes). `promoCode` sans `planCode` est rejeté dès la validation zod (`onboardTenantSchema.refine`) — un code promo n'a de sens qu'accompagné d'une souscription à créer. **Reste hors périmètre, assumé** : appliquer effectivement la remise (`discountType`/`discountValue`) au montant facturé — `PromotionCode` n'a pas de `currencyId`, donc un `FIXED_AMOUNT` ne peut pas être converti en centimes sans décision de schéma supplémentaire (quelle devise de référence ? conversion par pays ?). Pour l'instant la rédemption est tracée et comptée — ce que §31 demandait explicitement pour ce point — mais `createInvoiceForSubscription` ([payment.service.ts](../apps/api/src/modules/payments/payment.service.ts)) continue de facturer le plein tarif du plan.

**Statistiques et indicateurs commerciaux — tranche 9** (`stats-admin.service.ts`) : `GET /platform/stats/overview` (`?windowDays=`, défaut 30), lecture pure — aucun `recordAuditLog`, consulter des statistiques n'est pas une intervention dans un tenant au sens de §31. Couvre les métriques §18 (tableau de bord super-admin)/§32 (indicateurs commerciaux) qui ont une source de données réelle : établissements par statut (`Tenant.status`), abonnements par catégorie d'abonné et par statut (`Subscription` joint à `SubscriptionOwner.ownerType`), renouvellements attendus (abonnements `autoRenew` actifs dont `endsAt`/`trialEndsAt` tombe dans la fenêtre), licences sponsorisées par statut, revenu par devise/pays/type d'abonné/plan (agrégé en mémoire à partir des `PaymentTransaction` `SUCCEEDED`, remontées jusqu'à `Subscription` via `PaymentIntent → Invoice`, puis jusqu'au `Tenant`/`Organization` du `SubscriptionOwner` pour le pays), paiements échoués, taux de conversion (transitions `SubscriptionEvent` `TRIAL → ACTIVE` rapportées aux entrées en `TRIAL`) et taux de résiliation (`CANCELLED`/`REFUNDED` rapporté aux abonnements ayant un jour été actifs). **Revenu jamais sommé toutes devises confondues** : le schéma n'a pas de table de taux de change, chaque agrégat de revenu reste donc un tableau par devise (`{ currencyIsoCode, amountCents }`), jamais un total unique — cohérent avec §40 (aucune conversion inventée). **Explicitement hors périmètre, faute de modèle** : incidents techniques, flux d'activité générique, utilisation réelle du stockage (seul `SubscriptionPlan.storageQuotaMb` existe — un quota, pas une mesure d'usage) ; **taux de renouvellement** volontairement exclu aussi — rien dans le modèle actuel ne distingue un renouvellement d'un simple maintien en statut `ACTIVE` (pas de job de facturation périodique automatisé), l'exposer serait fabriquer un chiffre.

**Paramètres globaux — tranche 10** (`platform-setting-admin.service.ts`) : `GET /platform/platform-settings`, `GET/PUT/DELETE /platform/platform-settings/:key`. Comble le point resté hors périmètre après la tranche 9 (« aucun modèle au schéma pour ça »). Nouveau modèle `PlatformSetting` ([platform.prisma](../prisma/schema/platform.prisma)) : même forme clé/valeur que `TenantSetting` (extensible sans migration à chaque nouveau paramètre — durée d'essai par défaut, contact support, message de maintenance...) mais volontairement **pas** un `TenantSetting` avec `tenantId` nul : un `@@unique([tenantId, key])` dégénérerait (Postgres traite deux `NULL` comme non égaux dans un index unique, même piège que la tranche 6), donc `key` porte directement sa propre contrainte unique ici — pas de `tenantId` du tout. Conséquence sur la forme de l'API : contrairement aux tranches précédentes (CRUD par `id` généré), les routes sont adressées par `key` (identifiant métier déjà unique) et `PUT` fait un upsert plutôt qu'un `POST`/`PATCH` séparés — plus naturel pour un magasin de paramètres où l'appelant connaît la clé qu'il veut lire ou écrire. Même choix que les tranches 3-7 : la `justification` reste optionnelle, `recordAuditLog` trace quand même chaque écriture (`platform_setting.create`/`update`/`delete`).

**Élévation temporaire limitée dans le temps — tranche 11** (`tenant-elevation-admin.service.ts`) : `GET /platform/tenants/:id/elevations`, `POST /platform/tenants/:id/elevate`, `POST /platform/tenants/:id/elevations/:userRoleId/revoke`. Ferme le dernier volet transversal de §31 resté ouvert après la tranche 10 : autorisation/justification/audit/moindre privilège étaient déjà exercés depuis la tranche 1, mais rien n'écrivait encore `UserRole.expiresAt`/`justification`. `elevate` accorde à **l'acteur lui-même** (jamais à un tiers — un admin ne peut pas élever quelqu'un d'autre à sa place) un rôle _tenant-scoped_ (`Role.scope === "TENANT"`, 400 `INVALID_ROLE_SCOPE` sinon) sur le tenant ciblé, avec une durée en heures plafonnée à `MAX_ELEVATION_HOURS = 72` (400 sinon) et une justification **obligatoire** (contrairement aux tranches 3-10 : ici l'intervention correspond exactement au texte du cahier des charges — « une intervention d'un administrateur global dans un tenant » — donc `justifiedActionSchema` des tranches 1/2 s'applique, pas le choix "optionnelle" des tranches suivantes). Le contrôle d'accès (`activeRoleCodes`, [lib/authorization.ts](../apps/api/src/lib/authorization.ts)) filtrait déjà `expiresAt` sur toute vérification de rôle (platform ou tenant) — l'enforcement du "limité dans le temps" était donc déjà correct côté lecture, il ne manquait que l'écriture. Une élévation déjà active pour le même rôle est refusée (409 `ELEVATION_ALREADY_ACTIVE`) ; ré-élever après expiration fait un `upsert` sur `@@unique([userId, roleId, tenantId])` plutôt qu'un nouveau `create` (la ligne existe déjà, expirée). `revoke` avance `expiresAt` à maintenant plutôt que de supprimer la ligne — l'historique des élévations (actives ou expirées) reste consultable via `GET .../elevations`, jamais perdu. §31 est désormais couvert dans son intégralité (tranches 1 à 11) sur le volet super-administration décrit par le cahier des charges.

requireAuth
  → requirePlatformRole        (routes super-admin)
  → enforceTenantScope         (résout et verrouille le tenant de la requête)
  → requireTenantMembership

Chaque middleware ([apps/api/src/middleware/](../apps/api/src/middleware/)) est testable isolément. Aucun contrôleur ne fait sa propre vérification d'autorisation.

## Vérification email/téléphone à l'inscription — §34

Ferme le TODO de `auth.service.ts` (« require email verification before granting ACTIVE status ») : `registerUser` crée désormais le compte `PENDING` (défaut du schéma, jamais forcé à `ACTIVE`) et `login` refusait déjà tout statut différent d'`ACTIVE` (`403 ACCOUNT_NOT_ACTIVE`) — il ne manquait que le mécanisme d'activation lui-même. Deux nouvelles colonnes hachées sur `User` ([identity.prisma](../prisma/schema/identity.prisma)) : `emailVerificationTokenHash` (jeton opaque 32 octets, unique, TTL 24h) et `phoneVerificationCodeHash` (code à 6 chiffres salé avec l'email — un hash seul collisionnerait entre deux comptes sur seulement 10⁶ valeurs, TTL 15 min, uniquement si un `phone` est fourni à l'inscription). `§15` accepte l'un ou l'autre : vérifier l'email OU le téléphone suffit à faire passer le compte `PENDING → ACTIVE`, vérifier le second canal ensuite se contente de journaliser `*VerifiedAt` sans effet supplémentaire. Routes : `POST /auth/verify-email`, `POST /auth/verify-phone`, `POST /auth/resend-email-verification`, `POST /auth/resend-phone-verification`. **Aucun fournisseur email/SMS réel n'existe dans ce code** (même limite que Mobile Money §24, les codes d'activation §8 et les canaux de notification §28) : le jeton/code est renvoyé en clair dans la réponse d'inscription (et de renvoi), documenté plutôt que simulé silencieusement — un futur relais email/SMS n'aurait qu'à consommer cette même valeur au lieu de la retourner à l'appelant. **Reste hors périmètre** : vérification téléphone réellement _obligatoire_ pour certains rôles (le cahier des charges dit "si activée" — ici elle s'active simplement dès qu'un `phone` est fourni à l'inscription). MFA fait l'objet de la section suivante.

## Authentification multifacteur (MFA) — §34

Exerce `User.mfaEnabled`/`mfaSecretCiphertext`, présents au schéma depuis la Phase 2 mais jamais lus/écrits jusqu'ici. TOTP (`otplib`, compatible Google/Microsoft Authenticator) plutôt que SMS : le cahier des charges dit seulement "authentification multifacteur optionnelle" sans imposer de mécanisme, et un second facteur par SMS dépendrait d'un fournisseur qui n'existe pas dans ce code (même limite que §24/§28). Trois routes de gestion, toutes derrière `requireAuth`, dans [mfa.service.ts](../apps/api/src/modules/auth/mfa.service.ts) :

- **`POST /auth/mfa/setup`** : génère un secret TOTP, le chiffre (AES-256-GCM, [lib/encryption.ts](../apps/api/src/lib/encryption.ts) — premier utilitaire de chiffrement réversible de ce code, tout le reste de `lib/` étant à sens unique : mots de passe argon2, jetons/codes hachés) et le stocke dans `mfaSecretCiphertext`. `mfaEnabled` ne bascule pas encore ici — refusé (409) si déjà actif.
- **`POST /auth/mfa/enable`** : vérifie un premier code TOTP contre le secret déchiffré, puis seulement bascule `mfaEnabled` à `true` et génère 8 codes de secours à usage unique (nouveau modèle `MfaRecoveryCode`, haché comme `ActivationCode` §8 — sans eux, perdre l'appareil TOTP rendrait le compte irrécupérable, aucun canal email/SMS réel n'existant pour un canal de secours alternatif). Rendus en clair une seule fois dans la réponse.
- **`POST /auth/mfa/disable`** : exige le mot de passe **et** un code (TOTP ou de secours) — seul le mot de passe ne suffit pas à désactiver un second facteur, ça viderait son intérêt.

Le login change de forme si `mfaEnabled` : `POST /auth/login` renvoie `{mfaRequired: true, challengeToken}` au lieu des jetons directement (mot de passe déjà vérifié à ce stade, compteur d'échecs déjà remis à zéro). `challengeToken` est un JWT signé avec le même secret que l'access token mais une claim `typ: "mfa_challenge"` distinctive et un TTL de 5 min ([lib/jwt.ts](../apps/api/src/lib/jwt.ts)) — `verifyAccessToken` rejette explicitement tout jeton porteur de cette claim, pour qu'un défi MFA ne puisse jamais être rejoué comme un accès complet sur une route `requireAuth`. `POST /auth/mfa/verify` (`{challengeToken, code}`, sans authentification préalable — c'est justement le rôle du challenge token) accepte un code TOTP ou un code de secours (consommé, `usedAt` posé) et ne crée la session qu'à ce moment. Testé de bout en bout dans [auth-mfa.test.ts](../apps/api/src/test/integration/auth-mfa.test.ts).

## Appareils connectés et révocation de session — §15/§34

**Correctif (audit de couverture complet §1-§41)** : `Session` porte `userAgent`/`ipAddress`/`deviceLabel`/`revokedAt`/`revokedReason` depuis la Phase 2 (posés à chaque login/refresh, voir `createSession`), mais rien ne les exposait à l'utilisateur — §15 (« le parent doit pouvoir voir les appareils connectés, révoquer une session ») et §34 (« révocation des sessions, historique des connexions, gestion des appareils ») restaient non couverts. `logout` ne pouvait révoquer que la session dont le refresh token était présenté — aucun moyen de couper l'accès d'un appareil dont on n'a plus le refresh token sous la main (perte/vol). Fermé dans [auth.service.ts](../apps/api/src/modules/auth/auth.service.ts) :

- **`GET /auth/sessions`** (`requireAuth`) : liste les sessions actives (non révoquées, non expirées) de l'appelant, plus récemment utilisées d'abord — `id`/`userAgent`/`ipAddress`/`deviceLabel`/`createdAt`/`lastUsedAt`/`expiresAt` seulement, jamais `refreshTokenHash` (une capacité de rejeu, pas une donnée d'affichage).
- **`POST /auth/sessions/:id/revoke`** (`requireAuth`) : révoque une session par id plutôt que par refresh token. `updateMany` scopé sur `{id, userId}` plutôt qu'un `findUnique` suivi d'une vérification séparée — l'id d'une session appartenant à un autre utilisateur ne correspond simplement à aucune ligne pour cet appelant (404 `SESSION_NOT_FOUND`), jamais une confirmation d'existence via un 403, même convention que le reste du code (transferts, bulletins/reçus des portails).
- `deviceLabel` reste non renseigné (aucun appelant ne le pose) — dériver un nom d'appareil lisible depuis `userAgent` est un ajout distinct, non demandé explicitement par le cahier des charges au-delà de la liste brute.

Testé dans [auth-sessions.test.ts](../apps/api/src/test/integration/auth-sessions.test.ts) : deux connexions du même utilisateur apparaissent comme deux sessions distinctes, la révocation d'une session par id ne touche pas l'autre, et un utilisateur ne peut ni voir ni révoquer la session d'un autre (404).

## Limitation de débit — §34

**Correctif (audit de couverture complet §1-§41)** : absente jusqu'ici malgré une exigence explicite du cahier des charges. Deux limiteurs (`express-rate-limit`, [middleware/rateLimit.ts](../apps/api/src/middleware/rateLimit.ts)) : `apiRateLimiter` en backstop généreux (600 req/15 min par IP) sur toute l'API y compris les webhooks, et `authRateLimiter` plus strict (20 req/15 min) sur `/api/v1/auth/*` — complète, sans le remplacer, le verrouillage par compte déjà en place (§34, échecs de connexion), qui ne couvre ni le credential stuffing entre comptes différents ni le brute-force de codes de vérification/OTP. Les deux sont désactivés sous `NODE_ENV=test` (les suites d'intégration font délibérément des dizaines d'appels rapprochés contre la même instance d'app) plutôt que dimensionnés artificiellement haut pour les accommoder. Testé dans [rate-limit.test.ts](../apps/api/src/test/integration/rate-limit.test.ts) via `buildRateLimiter` (exporté pour ce seul usage) instancié avec `skip` désactivé — le seul moyen d'observer le mécanisme réellement engagé dans un process où `NODE_ENV` vaut toujours `test`.

## Validation des URLs de fichiers — §34

**Correctif (audit de couverture complet §1-§41)** : « protection des fichiers » est listée explicitement au §34 parmi les contrôles de sécurité minimaux. Six champs à travers le code (`StudentDocument.fileUrl`, `Student.photoUrl`, `EmployeeDocument.fileUrl`, `EmploymentContract.fileUrl`, `HomeworkSubmission.fileUrl`, `CourseResource.url`) suivent tous le même principe assumé et documenté ailleurs dans ce fichier (carte scolaire, §19) : une URL vers un fichier déjà téléversé ailleurs, jamais récupérée côté serveur — pas de risque SSRF. Mais jusqu'ici, la validation Zod de ces six champs se limitait à `z.string().min(1)` : n'importe quelle chaîne non vide passait, y compris un schéma `javascript:`/`data:`. Ces valeurs sont ensuite restituées telles quelles à d'autres utilisateurs authentifiés (un parent consultant les documents de son enfant, un enseignant consultant une soumission de devoir, un membre du personnel consultant un document RH) — un XSS stocké classique si un futur rendu client transforme le champ en lien cliquable. Fermé par [lib/http-url-schema.ts](../apps/api/src/lib/http-url-schema.ts) (`httpUrlSchema`, `z.string().url()` plus un `.refine()` qui vérifie explicitement `new URL(value).protocol` contre `http:`/`https:` — le seul moyen fiable, `.url()` seul acceptant n'importe quel schéma syntaxiquement valide), consommé par les six schémas concernés plutôt que dupliqué. Testé dans [students.test.ts](../apps/api/src/test/integration/students.test.ts) : un `fileUrl: "javascript:alert(document.cookie)"` est rejeté (400) avant même d'atteindre la base.

## Verrouillage effectif des abonnements/entitlements — §37

`requireActiveSubscription`/`requireEntitlement` ([lib/subscription-access.ts](../apps/api/src/lib/subscription-access.ts), [middleware/requireActiveSubscription.ts](../apps/api/src/middleware/requireActiveSubscription.ts), [middleware/requireEntitlement.ts](../apps/api/src/middleware/requireEntitlement.ts)) existaient déjà, testés isolément, mais n'étaient câblés sur **aucune route réelle** — un parent/élève sans abonnement actif pouvait donc consulter n'importe quelle fonction protégée du portail. Fermé en câblant les deux middlewares sur les routes concernées :

- **Portail parent** ([parent-portal.routes.ts](../apps/api/src/modules/parent-portal/parent-portal.routes.ts)) : `requireActiveSubscription(familyAccountOwnerContext)` sur chaque route `/children/:studentId/...`, toujours **après** `requireVerifiedStudentRelationship` (un étranger sans relation vérifiée reste bloqué par le 403 de relation, jamais un 402 d'abonnement qui confirmerait au passage l'existence d'un compte familial). Le téléchargement du bulletin en PDF utilise `requireEntitlement("report_card.download", ...)` à la place — seule action déjà dimensionnée avec un quota au seed (`plan-features.ts`). `GET /dashboard` reste volontairement **hors garde** : il doit rester consultable sans abonnement (il affiche `subscription: null` dans ce cas) — un aperçu, pas une fonction protégée au sens de §37.
- **Portail élève** ([student-portal.routes.ts](../apps/api/src/modules/student-portal/student-portal.routes.ts)) : même schéma avec `requireActiveSubscription(studentOwnerContext)` après `requireLinkedStudent`, même exception pour `/dashboard` et le téléchargement de bulletin (`requireEntitlement`).
- **Devoirs et e-learning** ([homework.routes.ts](../apps/api/src/modules/homework/homework.routes.ts), [elearning.routes.ts](../apps/api/src/modules/elearning/elearning.routes.ts)) : `requireActiveSubscription(studentOwnerContext)` après `requireLinkedStudent` sur les seules routes `/student/:studentId/...` — les routes staff (CRUD, `enforceTenantScope`/`requireTenantMembership`) restent inchangées.

**Correctif (audit de couverture complet §1-§41) — l'abonnement de l'établissement lui-même n'était vérifié nulle part (§3.1)** : le câblage ci-dessus couvrait les portails parent/élève et les routes self-service élève de devoirs/e-learning, mais `requireActiveSubscription(tenantOwnerContext)` — le résolveur par défaut, taillé précisément pour ce cas — n'était appelé sur **aucune route côté établissement**. §3.1 exige explicitement un abonnement actif pour « les modules administratifs, académiques, financiers et de communication » ; en pratique, un établissement dont l'abonnement passait `EXPIRED`/`CANCELLED` (ou n'en avait jamais eu, `createDraftSubscription` restant optionnel à l'onboarding) continuait d'utiliser indéfiniment finance, élèves, notes, présences, discipline, RH, emplois du temps, bibliothèque, transport, cantine, internat et le tableau de bord staff, tant que `TenantMembership.status` restait `ACTIVE` — le SaaS ne pouvait jamais réellement couper l'accès d'un établissement impayé. Fermé en ajoutant `requireActiveSubscription()` à la chaîne de garde partagée de chacun de ces routeurs (`finance`, `school-config`, `students`, `student-transfers`, `grading`, `attendance`, `discipline`, `employees`, `tenant-users`, `library`, `transport`, `cafeteria`, `boarding`, `dashboard`, et les routes staff de `homework`/`elearning`), toujours **après** `requireTenantMembership` — même position relative que les portails. Le fixture de test partagé `createTenant` (`apps/api/src/test/fixtures.ts`) provisionne désormais un abonnement `SCHOOL_ESSENTIAL` `ACTIVE` par défaut (paramètre `activeSubscription: false` pour les rares tests qui gèrent l'abonnement du tenant eux-mêmes, `SubscriptionOwner.tenantId` étant unique) — évite de dupliquer cette provision dans chacun des ~50 fichiers de test qui exercent des routes établissement. Testé de bout en bout sur deux modules représentatifs dans [tenant-subscription-gate.test.ts](../apps/api/src/test/integration/tenant-subscription-gate.test.ts) (aucun abonnement puis abonnement annulé → 402 sans effacer le tenant ; abonnement actif → 200). **Restent hors périmètre de ce correctif, par choix** : les routes staff de `family.routes.ts` (gestion des invitations/relations) et `communication.routes.ts` (annonces, tickets de support) ne sont pas gardées — bloquer l'accès aux tickets de support serait précisément couper le seul canal restant pour un établissement cherchant à régulariser un litige de facturation, un arbitrage produit distinct de ce correctif de sécurité.

**Nouveau resolveur** `familyAccountOwnerContext` (async, dans `subscription-access.ts`) : le parent peut ne pas encore avoir de `FamilyAccount` (abonnement en libre-service, jamais automatique §9) — un sentinel qui ne correspond à aucun `SubscriptionOwner` réel fait retomber sur 402 "pas d'abonnement actif", jamais un abonnement fabriqué ni le 403 générique que renverrait un contexte `null`. `OwnerContextResolver` a dû être élargi pour accepter une résolution asynchrone (`Promise<SubscriptionOwnerContext | null>`) — rétrocompatible avec les résolveurs synchrones existants (`tenantOwnerContext`, `studentOwnerContext`).

**Licence sponsorisée expirée/révoquée bloque désormais l'accès (§37 item 10)** : `SponsoredLicense.validUntil`/`status` et `LicenseAssignment.revokedAt` étaient capturés au schéma et mutés par `revokeLicense` (tranche 7, §31) mais jamais consultés — un abonnement financé par une licence sponsorisée révoquée restait `ACTIVE` indéfiniment. `findActiveSubscription` vérifie désormais qu'un `LicenseAssignment` non révoqué et non expiré existe pour cet abonnement dès qu'un `LicenseAssignment` quelconque lui est rattaché — sinon la subscription est traitée comme inactive (402).

**Correctif (audit de couverture complet §1-§41)** : la version initiale de ce contrôle ne se déclenchait que si `Subscription.fundingSource` valait `SCHOOL_SPONSORED`/`ORGANIZATION_SPONSORED` — or `license-admin.service.ts` (`assignLicense`) ne modifie délibérément jamais ce champ sur un abonnement existant (il se contente de tracer quelle licence couvre quel abonnement déjà créé par les flux self-service). Tout abonnement réellement couvert par une licence sponsorisée restait donc `SELF_PAID` en pratique, rendant le contrôle inopérant pour tout vrai bénéficiaire — seul un test qui fabriquait directement un abonnement `fundingSource: "SCHOOL_SPONSORED"` le faisait passer. Gouverné maintenant par la présence réelle d'un `LicenseAssignment`, jamais par le funding source déclaré. Testé par un nouveau cas reproduisant exactement l'état que laisse `assignLicense` (abonnement `SELF_PAID` + licence révoquée → 402).

**Quotas réellement consommés (§37 item 13)** : `requireEntitlement` incrémente désormais `Entitlement.quotaUsed` (`{ increment: 1 }`, jamais lecture-puis-écriture) après chaque appel réussi sur une fonctionnalité plafonnée (`quotaLimit` non nul) — jusqu'ici le compteur était lu mais jamais mis à jour, un quota ne pouvait donc jamais s'épuiser en pratique.

**Correctif (audit de couverture complet §1-§41) — un quota épuisé restait épuisé à vie, même après un renouvellement payé** : symétrique du point précédent — `quotaUsed` s'incrémentait bien, mais `recalculateEntitlements` ([subscriptions/subscription.service.ts](../apps/api/src/modules/subscriptions/subscription.service.ts)) ne le remettait jamais à zéro à aucune transition, y compris une réactivation après paiement régularisé. §6 exige que « les droits soient recalculés après chaque changement [de statut] » ; §37 exige que « les quotas soient respectés », ce qui suppose qu'ils se rechargent à la période suivante, pas qu'ils s'épuisent une fois pour toutes. `quotaUsed` est désormais remis à `0` précisément quand `toStatus === "ACTIVE"` — le même signal déjà utilisé juste au-dessus pour recalculer `currentPeriodEndsAt` (une nouvelle période de facturation qui commence), jamais sur les autres transitions (`GRACE_PERIOD`/`SUSPENDED` ne sont pas des renouvellements, seulement un arrêt de la consommation). Testé dans [subscription-access.test.ts](../apps/api/src/test/integration/subscription-access.test.ts) : un quota épuisé reste épuisé pendant une suspension, puis repart à zéro dès la réactivation.

Testé dans [subscription-access.test.ts](../apps/api/src/test/integration/subscription-access.test.ts) (licence valide/expirée/révoquée, incrémentation puis blocage de quota) et par les quatre suites de portail/devoirs/e-learning existantes, mises à jour pour créer un abonnement réel là où elles exerçaient jusqu'ici ces routes sans qu'aucun abonnement n'existe.

**Items 12 et 18 du checklist §37, audités puis fermés par un test, sans changement de code de production** — les deux étaient déjà correctement implémentés, seule la couverture de test manquait :

- **Item 12 — « le front ne peut pas forger son statut/plan »** : `createSchoolSubscriptionSchema`/`createFamilySubscriptionSchema`/`createStudentSubscriptionSchema` ([subscription.validation.ts](../apps/api/src/modules/subscriptions/subscription.validation.ts)) n'acceptent que `planCode`/`billingPeriod`/`promoCode` — Zod sans `.passthrough()` supprime silencieusement tout champ supplémentaire (`status`, `planId`, `fundingSource`...), et aucun contrôleur ne fait jamais `...req.body`. `subscription.controller.ts` fixe lui-même `status: "DRAFT"`, `fundingSource: "SELF_PAID"` et l'`ownerRef` (résolu côté serveur, jamais depuis le corps de la requête) ; `planId` est toujours résolu depuis `planCode` avec vérification de catégorie (`PLAN_CATEGORY_MISMATCH`). Il n'existe aucune route PATCH sur `Subscription` — le seul changement de statut atteignable par un client self-service est `/cancel`, qui cible toujours `"CANCELLED"` en dur. Testé par un nouveau cas dans [student-subscription.test.ts](../apps/api/src/test/integration/student-subscription.test.ts) et [family-subscription.test.ts](../apps/api/src/test/integration/family-subscription.test.ts) : un corps de requête forgé (`status`, `planId` d'un autre plan, `fundingSource` sponsorisé, `trialEndsAt`) est entièrement ignoré, la ligne créée reste `DRAFT`/`SELF_PAID`/le plan réellement demandé.
- **Item 18 — atomicité des transactions financières** : chaque opération multi-écriture qui touche de l'argent est déjà dans une seule transaction — `createInvoiceForSubscription`/`recordManualCashPayment`/`processWebhookEvent` (`payment.service.ts`, `prisma.$transaction`) côté SaaS, `recordCashPayment`/`refundStudentPayment` (`student-payment.service.ts`, `withTenantSession`) côté frais scolaires. Prouvé, plutôt que simplement documenté, par [payment-atomicity.test.ts](../apps/api/src/test/integration/payment-atomicity.test.ts) : `generateReference` ([payments/reference.ts](../apps/api/src/modules/payments/reference.ts)) est mocké pour échouer sur son tout dernier appel dans chacun des deux flux (numérotation du reçu — la dernière écriture de la transaction), puis on vérifie qu'aucune écriture antérieure n'a survécu (paiement, mise à jour du solde de facture, activation d'abonnement) avant de lever le mock et de constater que l'opération réussit normalement ensuite.
